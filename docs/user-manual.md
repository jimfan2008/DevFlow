# DevFlow 用户使用手册

## 项目创建流程

### 1. 创建项目

1. 登录 DevFlow 平台
2. 点击 **新建项目**
3. 填写项目信息：
   - 项目名称（唯一）
   - 项目描述
   - 技术栈（可选）
   - 截止日期（可选）
4. 系统自动创建：
   - 需求评审群组
   - 项目看板（含4列：待处理→进行中→测试中→已完成）
   - Gitea 代码仓库（含 main/develop 分支）

### 2. 提交需求

1. 进入项目详情页
2. 点击 **需求管理**
3. 编写需求内容（支持多次迭代修改）
4. 每次修改自动递增版本号

### 3. 启动需求评审会议

1. 进入项目群聊
2. 点击 **启动会议**，选择会议类型：
   - 需求评审：逐条审查需求文档
   - 技术方案评审：架构与选型论证
   - 每日站会：进度同步
   - 故障复盘：根因分析
3. Hermes Agent 自动主持，按议程推进
4. 人类用户可随时介入发言
5. 会议结束后生成纪要（决议、待办、风险、未决事项）

### 4. 锁定需求

1. 会议达成共识后，点击 **确认并锁定需求**
2. 需求锁定后不可修改（除非锁定者本人）
3. 系统自动触发：
   - 任务拆解（Celery异步）
   - 项目仓库创建

## 需求评审会议

### 会议类型

| 类型 | 议程 | 主持人裁决 | 共识要求 |
|------|------|-----------|---------|
| 需求评审 | 文档审查→矛盾识别→验收确认→建议汇总 | 是 | 否 |
| 技术方案 | 方案介绍→选型论证→风险评估→方案决议 | 是 | 否 |
| 每日站会 | 昨日完成→今日计划→风险阻碍 | 否 | 否 |
| 故障复盘 | 时间线还原→根因分析→改进措施→责任确认 | 是 | 是 |

### 会议操作

- **介入发言**：人类用户可在会议中发言，不影响议程
- **争议处理**：由主持人裁决或记录待讨论
- **主持人离线**：会议自动暂停，等待恢复

## 任务看板

### 看板列

| 列 | 说明 |
|----|------|
| 待处理 | 新创建的待执行任务 |
| 进行中 | Agent正在执行的任务 |
| 测试中 | 等待验收的任务 |
| 已完成 | 验收通过的任务 |

### 任务状态流转

```
待处理 → 已分配 → 执行中 → 已交付 → 已验收
                                    ↘ 已驳回 → 重新分配
```

### 任务信息

每个任务包含：
- 任务名称和描述
- 优先级（高/中/低）
- 建议的 Agent 类型
- 验收标准
- 当前执行进度
- 分配的编程 Agent
- 依赖关系（DAG）

### 任务依赖

任务之间可以建立依赖关系，形成有向无环图（DAG）：
- 系统自动检测循环依赖
- 支持拓扑排序查看执行顺序
- 前置任务未完成时，后续任务不可执行

## 代码仓库

### Git Flow 模型

```
main (受保护，2人审核)
  └── develop (受保护，1人审核)
        ├── feature/xxx
        ├── release/x.x
        └── hotfix/xxx
```

### Conventional Commits 规范

提交消息必须遵循：

```
<type>(<scope>): <description>

type: feat | fix | docs | style | refactor | perf | test | build | ci | chore | revert
```

示例：
- `feat(auth): add OAuth2 login support`
- `fix(api): resolve token refresh issue`
- `docs: update deployment guide`

DevFlow 自动校验提交消息格式。

### Pull Request 流程

1. 从 `develop` 创建功能分支
2. 完成开发后创建 PR 到 `develop`
3. 通过代码审查和CI检查
4. 合并到 `develop`
5. 发布时从 `develop` 合并到 `main`

## 人类用户角色边界

### 人类用户职责

| 职责 | 说明 |
|------|------|
| 项目创建 | 创建项目、设定目标和约束 |
| 需求编写 | 编写和修改需求文档 |
| 需求评审 | 参与评审会议、介入讨论 |
| 需求锁定 | 确认并锁定需求 |
| 验收决策 | 对自动验收结果进行最终确认 |
| 争议仲裁 | 在Agent间争议时做出最终裁决 |
| 紧急介入 | 紧急情况下暂停/接管任务 |

### Hermes Agent 职责

| 职责 | 说明 |
|------|------|
| 会议主持 | 按议程推进评审会议 |
| Agent协调 | 发现、对接、调度编程Agent |
| 任务拆解 | 根据需求自动拆解为原子任务 |
| 成果验收 | 自动化验收（覆盖度、测试通过率等） |
| 通知推送 | 多渠道通知（平台/邮件/短信） |

### 编程 Agent 职责

| 职责 | 说明 |
|------|------|
| 代码编写 | 按任务要求编写代码 |
| 测试编写 | 编写单元测试和集成测试 |
| 代码修复 | 根据驳回意见修复代码 |

### 边界规则

1. **人类不直接指挥编程Agent**：所有指令通过 Hermes Agent 的 Skill 层传递
2. **编程Agent不直接汇报给人类**：所有反馈通过 Skill-接收 传递到系统
3. **人类可在会议中介入**：但不会打断 Agent 工作流程
4. **连续驳回升级**：任务被连续驳回3次以上，自动通知人工介入
5. **需求锁定后不可修改**：除非锁定者本人操作
