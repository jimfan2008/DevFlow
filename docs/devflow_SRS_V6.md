## 1. 引言

### 1.1 目的

本文档定义 DevFlow 项目管理平台的功能需求、非功能需求及系统架构，核心聚焦于"AI Agent 全自动开发软件"的16步标准流程。该流程确保9个命名AI Agent角色严格按照既定步骤执行，每个Agent通过项目讨论群实现高效沟通与协作，每步产出经QA门控检验，保障软件交付质量。本文档作为开发团队实施和测试验收的依据。

### 1.2 范围

DevFlow 是一个面向人类用户与 AI Agent 协同的全自动化软件开发项目管理平台，核心功能包括：项目创建、需求分析、架构设计、开发环境搭建、TDD测试用例编写、代码编写、测试验证、安全审计、部署交付、文档管理、QA门控的全流程自动化。平台通过9个命名Agent角色紧密协作，在项目讨论群中实时沟通，确保每个Agent都按流程执行，共同完成软件项目的全自动开发。

#### 2.3.2 Agent协作与沟通机制

DevFlow 中所有Agent通过以下机制实现高效的相互沟通与协作：

**（1）项目讨论群（核心沟通渠道）**

项目创建后（第二步），海梅自动建立项目讨论群，将所有9个命名Agent角色加入群组。项目讨论群是Agent间沟通的核心渠道，支持两种工作模式：

* **讨论模式**：Agent自由发言，通过 `@Agent名称` 定向沟通，所有讨论内容实时广播
* **会议模式**：由海梅主持结构化会议（如需求评审会、技术方案讨论会），按议程逐项讨论，产出结构化纪要

**（2）海梅统一协调（任务分派中枢）**

海梅作为项目经理，是流程的总调度者：

* 负责向各Agent分派任务、指定输入和产出要求
* 通过项目讨论群发布任务分派指令
* 监控各Agent执行进度，协调Agent间的交接
* 对项目的整体交付成果负责

**（3）QA门控（质量保障枢纽）**

后荣（QA）作为质量门控，贯穿整个流程：

* 每个产出的检验是Agent间交接的必经环节
* 检验合格：后荣放行，产出提交代码库，海梅安排下一步
* 检验不合格：后荣退回重做，附带修改建议，Agent修改后重新提交检验

**（4）代码库（共享成果仓库）**

Gitea代码库是所有Agent共享的成果存储中心：

* 每次检验合格的产出品全部提交到代码库
* Agent可以随时查阅代码库中的上游产出文档
* 后贵（文档管理员）负责保证所有文档与代码的一致性

**（5）任务依赖联动（自动化交接）**

有依赖关系的任务按依赖图自动联动：

* 前置任务完成并通过QA检验后，自动触发后继任务
* 前后两个任务必须分配给不同的Agent执行
* 依赖联动日志全程记录

#### 2.3.3 命名Agent部署模型

9个命名Agent角色采用独立Profile实例部署模式：

* **独立进程**：每个命名Agent角色对应独立的Hermes Agent Profile实例，拥有独立的配置文件（config.yaml）、独立的Gateway端口、独立的模型配置
* **Profile存储路径**：`~/.hermes/profiles/{profile_name}/`（如 `haimei/`、`houxing/`、`houwang/` 等）
* **Gateway通信**：各Agent通过各自的Gateway端口暴露REST API + WebSocket接口，DevFlow平台通过Gateway API与各Agent通信
* **端口分配**：默认端口范围 8765-8773，每个Profile实例占用一个端口
* **进程管理**：各Agent进程独立启动、独立运行、独立停止，互不影响

### 2.4 运行环境

* 前端: 现代浏览器 (Chrome 90+, Firefox 88+, Safari 14+)

* 后端: Linux/Windows/macOS (Docker 部署)

* 数据库: PostgreSQL 14+, Redis 6+

* 代码托管: 本地部署 Gitea（轻量级自托管 Git 服务）

* AI Agent 交互层: 通过 Hermes Gateway API 与 Hermes Agent 通信

* Hermes Profiles 路径配置:
  
  * Windows: `\\wsl$\{distro}\home\{user}\.hermes`（通过 WSL 路径访问）
  * Linux/macOS: `~/.hermes`

* Hermes Agent:

## 3. AI Agent 全自动开发流程（16步标准流程）

> **核心原则**：
> 
> 1. 每步产出必须经 HouRong（后荣/QA）检验合格方可进入下一步
> 2. 检验合格的产出品全部提交到代码库
> 3. 检验不合格的产出品退回重做，直到合格
> 4. 所有Agent通过项目讨论群进行实时沟通和协作
> 5. 海梅（项目经理）负责任务分派，对项目的交付成果负责
> 6. 第一步由人类用户执行，无需QA门控

### 第一步：人类用户创建新的软件项目

* **执行者**: 人类用户

* **输入**: 项目名称、项目描述、初始需求

* **处理**:
  
  1. 人类用户在 DevFlow 平台创建新的软件项目
  2. 填写项目名称（必填）、项目描述（可选）、初始需求（可选）
  3. 系统生成唯一项目 ID，存储项目基础信息
  4. 系统在 Gitea 中自动创建项目代码仓库
  5. 系统自动创建项目文件夹，路径为 `/DevFlow/projects/{project_id}/`

* **产出成果**: 项目创建成功，创建项目文件夹，创建代码仓库

* **业务规则**:
  
  * 项目名称需唯一
  * 支持富文本/Markdown 需求描述，支持附件上传（原型图、需求文档等）
  * 项目ID命名规则：`proj-{YYYYMMDD}-{sequence}`（如 `proj-20260612-001`）

> **注**：第一步由人类用户执行，产出不需要QA门控检验，无需提交代码库。

### 第二步：海梅主动与人类用户对话，确认项目核心目标并搭建组织架构

* **执行者**: HaiMei（海梅），项目经理

* **输入**: 人类用户的项目描述和初始需求

* **处理**:
  
  1. 海梅主动与人类用户对话，沟通并确认项目的核心目标
  2. 搭建项目组织架构，激活9个命名Agent角色：

| ------- | --- | -------- | ----------------------------------------- |

| HouXing | 后兴  | 需求分析师    | 负责需求分析，产出完整、准确的软件需求说明书                    |
| HouWang | 后旺  | 架构设计师    | 负责架构设计、后端设计、前端设计、数据库设计等                   |
| HouFa   | 后发  | 程序员      | 负责建立代码编写Agent蜂群，监督蜂群完成TDD测试用例和代码编写        |

### 第三步：海梅安排后兴与用户对话，产出软件需求说明书

* **执行者**: HaiMei（海梅）安排 HouXing（后兴）— 需求分析师

* **Agent协作**: 海梅在项目讨论群中 @后兴，分派需求分析任务；后兴接收任务后与人类用户对话

* **输入**: 项目核心目标、用户初始需求

* **处理**:
  
  1. 海梅安排后兴（Hermes Agent — 需求分析师角色）一起与人类用户对话，沟通具体需求
  2. 如果项目较复杂（满足复杂项目判断标准之一：功能需求项数>20项、涉及技术栈>3种、预计开发周期>2周、用户明确要求），在项目讨论群中召开需求评审会议（会议类型：`requirement_review`），海梅主持，后兴记录
  3. 后兴根据沟通结果和会议纪要，生成完整、准确的软件需求说明书（SRS）

* **产出成果**: 完整、准确的软件需求说明书（SRS），适于拆解成开发任务清单

* **QA门控**: 软件需求说明书必须经 HouRong（后荣/QA）检验合格才可以进行下一步。后荣按以下四个维度逐项检验并返回检验结果：
  **（1）完整性检验**：检查SRS是否包含以下12项必查内容，每项存在计1分，缺失计0分，完整性得分 = (存在项数 / 12) × 100：
  ①引言（目的、范围、术语定义） ②整体描述（产品愿景、用户角色） ③功能需求（按模块组织，每项含输入/处理/输出/业务规则） ④非功能需求（性能、安全、可用性） ⑤验收标准（可执行的检查清单） ⑥系统架构（技术栈、架构图） ⑦数据库设计（表结构、字段定义） ⑧接口需求（API端点、参数、响应） ⑨运行环境描述 ⑩业务流程图或流程图 ⑪约束条件和假设 ⑫变更日志
  **（2）一致性检验**：检查SRS内部是否存在以下6类矛盾，每发现1处矛盾计1个矛盾项，矛盾项总数=0则检验通过：
  ①术语定义与正文使用不一致 ②功能需求描述与非功能需求约束冲突 ③同一功能在不同章节描述不一致 ④数据库字段定义与API接口参数不一致 ⑤验收标准与功能需求描述不匹配 ⑥流程图与文字描述不一致
  **（3）可验证性检验**：检查SRS中所有验收标准是否符合以下7条判定规则，每条规则达标计1分，可验证性得分 = (达标规则数 / 7) × 100：
  ①验收标准使用可量化的数值（如"响应时间<2秒"而非"响应快速"） ②验收标准包含明确的测试方法描述 ③验收标准有明确的通过/失败判定条件 ④验收标准不包含主观判断词（如"良好的"、"合理的"、"适当的"） ⑤验收标准可对应到具体的测试用例 ⑥验收标准的测量工具和测量环境已定义 ⑦验收标准的合格阈值已明确定义
  **（4）无歧义性检验**：检查SRS是否存在以下5类模糊表述，每发现1处模糊表述计1处，模糊表述总数=0且术语表完整性≥95%则检验通过：
  ①使用"可能"、"也许"、"大约"等不确定词汇 ②使用"等"、"之类"、"相关"等模糊范围词 ③使用"快速"、"高效"、"良好的"等主观形容词无量化定义 ④使用"支持"但未说明支持的具体范围和程度 ⑤使用"用户"但未区分用户角色类型。同时检查术语表中所有专业术语是否已在1.3节定义（术语表完整性 = 已定义术语数 / 总术语数 × 100，要求≥95%）

* **代码库提交**: 检验合格的软件需求说明书提交到代码库

* **业务规则**:
  
  * 需求说明书必须包含：功能需求、非功能需求、验收标准、约束条件
  * 复杂项目必须召开需求评审会议（多Agent协同讨论）
  * 生成的需求文档，必须保存到项目文件夹的 `docs/` 子目录下
  * 需求说明书需人类用户确认
  * 后荣检验维度：需求完整性、一致性、可验证性、无歧义性（详见4.3.1节量化打分标准和上述四个维度的检验子项清单）
  * QA检验不合格的，将检验报告发给 HouXing（后兴），要求 HouXing（后兴）按检验报告在规定时限（24小时）内修改，直到QA检验合格，才能进行下一步

## 4. 功能需求（支撑模块）

### 4.1 项目讨论群与多Agent协作模块

#### 4.1.1 群组管理

* **功能描述**: 创建和管理由9个命名Agent角色组成的项目讨论群，作为Agent间沟通与协作的核心渠道

* **群组属性**:
  
  * 基本信息：群组名称、描述、创建时间
  * 成员列表：HaiMei, HouXing, HouWang, HouFa, HouDa, HouFu, HouGui, HouRong, HouHua
  * 工作模式：`discussion`（讨论模式）或 `meeting`（会议模式）
  * 主持人：会议模式下的 Host Agent（默认海梅）

* **支持的操作**:
  
  * 自动创建：项目第二步自动创建群组，所有Agent自动加入
  * 查看群组：获取群组详情和成员列表
  * 修改群组：更新名称、描述、成员、主持人
  * 成员管理：添加/移除成员，设置主持人

* **业务规则**:
  
  * 每个项目必须有一个项目讨论群
  * 所有9个命名Agent角色必须加入讨论群
  * 会议模式必须设置主持人

#### 4.1.2 讨论模式 (Discussion Mode)

* **功能描述**: 群组的自由工作模式，Agent成员可自主发言、回复消息，是实现Agent间日常沟通的主要方式

* **消息发送**:
  
  * 人类用户或Agent可随时在群组中发送消息
  * 支持 `@Agent名称` 定向提及特定Agent（如海梅 @后兴 分派任务）
  * 未提及Agent时，所有成员都会收到消息并回复

* **自动回复机制**:
  
  * 检测消息中的 @mention
  * 确定目标回复Agent
  * 获取最近消息作为上下文
  * 调用 Gateway API 获取各Agent的响应
  * 流式输出响应内容到前端

* **消息存储**:
  
  * 所有消息持久化到数据库
  * 记录发送者、角色、内容、时间戳
  * 支持历史消息查询

#### 4.1.3 会议模式 (Meeting Mode)

* **功能描述**: 群组的结构化工作模式，由海梅（主持人）控制议程，产出结构化会议成果。用于需求评审会、技术方案讨论会等需要多Agent集中讨论的场景

* **会议类型**:
  
  * 需求评审会 (requirement_review): PRD整体介绍→业务流程→边界规则→特殊场景→开发提问→当场确认
  * 技术方案讨论会 (tech_solution): 背景目标→现有问题→备选方案对比→架构接口→敲定方案→拆分任务
  * 每日站会 (daily_standup): 每人3句话（昨天/今天/阻塞）
  * 故障复盘会 (incident_postmortem): 时间线→影响面→根因→修复措施→预防改进

* **会议流程**:
  
  1. 开场定调：主持人介绍会议目标、产出要求
  2. 制订议程：主持人根据会议类型生成可执行议程
  3. 按议程讨论：按顺序邀请各成员发言，主持人控场
  4. 会议总结：主持人输出结构化会议纪要

* **会议规则**:
  
  * 聚焦议题，不跑偏
  * 发言简明，每人限时
  * 争议无共识由海梅（主持人）当场拍板
  * 结论当场记录

* **用户干预**: 会议进行中人类用户可发送消息干预，主持人可调整议程

* **输出**: 会议纪要、决议、待办任务、风险点、遗留问题

### 4.2 Agent蜂群管理模块

#### 4.2.1 蜂群建立与管理

* **功能描述**: 后发（代码编写）或后达（代码测试）建立编程Agent蜂群，调度多个编程Agent并行执行任务

* **蜂群成员**: 可以是以下任意编程Agent：
  
  * Claude Code
  * Codex
  * Opencode
  * Cursor
  * CodeArts
  * Trae
  * Lingma
  * hermes子agent
  * pi-codeing-agent子agent

* **蜂群调度者**:
  
  * 后发（HouFa）：代码编写蜂群调度（第七步TDD测试用例、第九步功能代码）
  * 后达（HouDa）：代码测试蜂群调度（第十一步全面测试）

* **蜂群管理功能**:
  
  * 任务分发：将原子化任务分配给蜂群中技能匹配的Agent
  * 进度监控：实时监控每个蜂群Agent的执行进度
  * 成果收集：收集每个蜂群Agent的交付成果
  * 负载均衡：根据Agent负载和技能匹配动态调整任务分配

#### 4.2.2 蜂群Agent生命周期

蜂群Agent经历以下生命周期阶段：

1. **启动阶段**：后发或后达通过 `POST /api/swarms` 创建蜂群时，DevFlow平台根据任务类型和数量自动选择并启动合适的编程Agent。启动方式：(a)对于Hermes子agent，通过Gateway API创建子会话 (b)对于外部编程Agent（Claude Code等），通过其CLI或API启动独立进程

2. **初始化阶段**：Agent启动后执行以下初始化步骤：(a)加载项目上下文（需求说明书、设计文档、代码编写计划等） (b)通过 `POST /api/agents/register` 向DevFlow平台注册自身信息和可用技能 (c)建立与DevFlow平台的通信连接（HTTP REST API） (d)加入项目讨论群（仅接收消息，不主动发言，除非被调度者@mention）

3. **执行阶段**：Agent接收后发/后达分派的任务，通过任务执行接口接收任务详情、执行代码编写或测试任务、定期上报进度、完成后交付成果

4. **退出阶段**：满足以下任一条件时Agent退出：(a)任务完成且成果已通过QA检验（正常退出） (b)蜂群调度者手动解散蜂群 `DELETE /api/swarms/:id`（手动退出） (c)Agent执行超时超过30分钟，自动终止当前执行并触发重试机制（最多重试3次，3次均失败后执行超时退出） (d)Agent进程异常崩溃（异常退出，调度者自动记录并更换备用Agent）

5. **资源清理**：Agent退出后，DevFlow平台自动清理其临时文件、断开通信连接、释放占用的计算资源

* **综合评分计算公式**: score = Σ(维度_i得分 × 权重_i) / Σ(权重_i)，其中各维度权重默认均等（权重_i = 1），即 score = 各维度得分的算术平均值。当某维度为布尔型指标（如"矛盾项=0"）时，达标记为100分，不达标记为0分。

#### 4.3.2 代码库提交规则

* **功能描述**: 检验合格的产出品全部提交到代码库（Gitea），作为Agent间的共享成果

* **提交规则**:
  
  * 所有检验合格的产出必须提交到Gitea代码库
  * 提交必须遵循Conventional Commits规范
  * 提交必须关联任务ID和QA检验记录ID
  * 未检验或检验不合格的产出禁止提交

* **提交时机**:

### 5.2 安全要求

* 用户认证: JWT Token 认证
* 授权控制: 基于角色的访问控制 (RBAC)，人类用户仅可查看/操作自身发起的项目
* 数据加密: HTTPS传输加密，Agent交互数据脱敏存储
* 成果安全: 项目代码/成果仅对人类用户和授权Agent可见
* 日志审计: 记录所有Agent交互、任务分配、QA检验操作日志
* 安全审计: 后华负责代码审计、合规审查、渗透测试、漏洞修复

### 5.3 可用性要求

* 系统可用性: 99.5%

* 数据备份: 详见5.6节备份策略

* 容错机制:
  
  * Agent执行失败时，海梅自动重试，最多重试3次
  * 重试间隔：首次重试等待30秒，第二次等待60秒，第三次等待120秒（指数退避）
  * 3次重试均失败后，海梅切换备用Agent执行
  * 备用Agent选择策略：(1)优先选择同类型且当前负载最低的Agent (2)若无同类型Agent，选择技能匹配度≥80%的其他Agent (3)若无可用的备用Agent，海梅通知人类用户并暂停该任务
  * Agent执行超时阈值：30分钟。超时后自动终止当前Agent执行，触发重试或备用Agent切换机制
  * 所有容错操作记录到日志表，供后荣检验和后贵文档归档

* 错误处理: 关键流程失败时提供明确错误提示和人工介入入口

* WebSocket断线后可自动重连并恢复群组订阅

### 5.4 可扩展性要求

* API接口设计遵循RESTful规范，支持新增编程Agent类型的快速接入
* 任务拆解规则支持配置化扩展（适配不同开发流程）
* 验收标准支持自定义扩展（适配不同技术栈/行业规范）
* 前端组件化设计，支持功能模块快速迭代
* 单个群组支持至少 10 个 Agent 同时在线

### 5.5 系统监控、告警和可观测性

* **Metrics（指标采集）**:
  
  * 系统级指标：CPU使用率、内存使用率、磁盘IO、网络带宽（采集间隔30秒）
  * 应用级指标：API响应时间P50/P95/P99、QPS、错误率、活跃连接数（采集间隔10秒）
  * Agent级指标：任务执行时长、任务成功率、Agent负载、蜂群Agent活跃度（采集间隔30秒）
  * 业务级指标：项目数、活跃项目数、QA检验通过率、各步骤平均耗时（实时统计）
  * 存储：Prometheus时序数据库，保留30天

* **Tracing（链路追踪）**:
  
  * 采用OpenTelemetry标准，为每个Agent任务分配唯一Trace ID
  * 追踪范围：从海梅分派任务开始，经过蜂群Agent执行、QA检验、代码提交的全链路
  * 存储：Jaeger后端，保留7天

* **Logging（日志管理）**:
  
  * 日志级别：DEBUG/INFO/WARN/ERROR/FATAL
  * 日志格式：JSON结构化日志，包含timestamp、level、service、trace_id、message、context
  * 日志存储：本地文件（按天轮转，保留30天）+ ELK Stack集中管理（保留90天）
  * 关键操作必须记录日志：Agent任务分派、QA检验结果、代码提交、错误和异常

* **告警规则**:
  
  * 系统级告警：CPU&gt;85%持续5分钟、内存&gt;90%持续3分钟、磁盘&gt;80%
  * 应用级告警：API错误率&gt;5%、P95响应时间&gt;5秒、连续10个Agent任务失败
  * Agent级告警：Agent进程宕机、连续3次重试失败、单个任务执行超过30分钟
  * 告警方式：平台内通知（WebSocket推送）+ 邮件（可选配置）
  * 告警升级：首次告警通知系统管理员，30分钟内未处理则通知项目人类用户

### 5.6 容灾恢复和备份策略

* **RTO（恢复时间目标）**: 系统故障后2小时内恢复服务

* **RPO（恢复点目标）**: 数据丢失不超过最后一小时内

* **备份范围**:
  
  * 数据库：PostgreSQL全部数据（项目数据、Agent数据、QA记录、群聊消息等）
  * 文件存储：项目文件夹下的所有文档、配置、报告
  * 代码仓库：Gitea完整仓库数据（含所有分支、PR、提交历史）
  * 配置文件：DevFlow应用配置、Hermes Profile配置

* **备份频率**:
  
  * 数据库：全量备份每日凌晨2:00执行，增量备份每6小时执行
  * 文件存储：每日凌晨3:00全量备份
  * 代码仓库：Gitea自带Git历史即版本备份，额外每日凌晨4:00完整归档

* **备份保留周期**:
  
  * 每日备份：保留30天
  * 每周备份（每周日凌晨）：保留90天
  * 每月备份（每月1日凌晨）：保留365天

* **备份存储**: 本地磁盘（/data/backups/）+ 可选远程存储（配置文件中指定）

* **恢复演练**:
  
  * 每季度进行一次完整恢复演练
  * 演练步骤：(1)从最新备份恢复数据库 (2)恢复文件存储 (3)恢复Gitea仓库 (4)验证应用功能正常 (5)记录恢复时间和数据完整性
  * 演练结果记录到日志，由系统管理员审核

### 5.7 多用户并发资源隔离和调度策略

* **资源隔离**:
  
  * 项目级别隔离：每个项目的Agent执行在独立的会话空间中运行，数据、文件、临时目录互不干扰
  * Agent并发限制：同一Agent Profile同一时间只能执行一个项目的任务（避免上下文冲突）
  * 蜂群Agent隔离：不同项目的蜂群Agent使用独立的临时工作目录（`/tmp/devflow/{project_id}/`）
  * 数据库隔离：通过project_id字段实现逻辑隔离，用户只能访问自己发起的项目数据

* **调度策略**:
  
  * 优先级队列：按项目创建时间FIFO调度，紧急项目（用户标记）可提升优先级
  * 并发限制：系统同时支持最多20个项目执行，超出队列等待
  * Agent分配策略：当多个项目同时需要同一类型Agent时，按优先级队列分配；若Agent正忙，任务进入等待队列
  * 超时回收：任务等待超过30分钟未分配到Agent，自动通知人类用户并释放资源

### 5.8 数据迁移策略和版本升级方案

* **数据迁移**:
  
  * 场景：数据库结构变更、存储引擎迁移、数据清洗
  * 方式：编写迁移脚本（Python + SQLAlchemy Alembic），支持正向迁移和回滚
  * 流程：(1)备份当前数据 (2)在测试环境执行迁移脚本验证 (3)迁移通过后在生产环境执行 (4)验证数据完整性 (5)保留旧版本数据7天以备回滚
  * 迁移日志：每次迁移记录迁移ID、执行时间、执行结果、影响数据量

* **版本升级**:
  
  * 发布策略：语义化版本控制（MAJOR.MINOR.PATCH），如 1.2.3
  * 兼容性：MINOR版本升级保证API向后兼容，MAJOR版本可能引入不兼容变更
  * 升级流程：(1)发布升级公告（含变更说明和兼容性提醒） (2)用户备份数据 (3)执行Docker镜像更新（`docker pull` + `docker-compose up -d`） (4)自动执行数据库迁移脚本 (5)运行健康检查验证升级成功 (6)若健康检查失败，自动回滚到上一版本
  * 回滚机制：保留最近3个版本的Docker镜像标签，支持一键回滚

### 5.9 国际化/多语言支持

* **支持语言**: 简体中文（默认）、English（英文）
* **前端国际化**: 使用Vue I18n实现前端多语言切换，语言包存储在 `public/locales/` 目录下
* **后端国际化**: API响应中的错误消息、提示文本支持多语言，通过Accept-Language请求头自动切换
* **Agent交互**: 命名Agent角色支持中英文双语交互，人类用户使用何种语言，Agent以相同语言回复
* **切换机制**: 用户可在个人设置中切换界面语言，切换后前端立即生效，无需刷新页面

### 5.10 无障碍访问

* **标准遵循**: WCAG 2.1 Level AA
* **键盘导航**: 所有交互元素支持键盘操作（Tab导航、Enter/Space激活）
* **屏幕阅读器**: 所有图像和图标提供alt文本，表单控件关联label，ARIA标签正确设置
* **颜色对比度**: 文字与背景对比度≥4.5:1（正常文字）、≥3:1（大文字）
* **字体缩放**: 支持浏览器字体缩放至200%而不破坏布局
* **焦点管理**: 页面切换时焦点自动定位到主要内容区域，模态弹窗关闭后焦点返回触发元素

### 6.3 数据库设计概要

#### 核心表

1. **users** - 人类用户表
   
   * id, username, email, password_hash, role, created_at

2. **projects** - 项目表
   
   * id, name, description, creator_id, core_goal, status, current_step(1-16), created_at, completed_at

3. **requirements** - 需求表
   
   * id, project_id, content, version, is_locked, confirmed_at

4. **agents** - Agent角色表（9个命名Agent + 编程Agent蜂群）
   
   * id, name(唯一), agent_type(named/swarm), role_name, chinese_name, status(online/offline/busy), api_endpoint, config(JSON), created_at

5. **tasks** - 任务表
   
   * id, project_id, name, description, type, priority, assignee_agent_id, status, acceptance_criteria, step_number(1-16), is_atomic, parent_task_id, created_at, completed_at

6. **task_dependencies** - 任务依赖表
   
   * id, source_task_id, target_task_id, dependency_type, created_at

7. **agent_execution_logs** - Agent执行日志表
   
   * id, task_id, agent_id, execution_content, result, created_at

8. **qa_records** - QA检验记录表（后荣检验记录）
   
   * id, task_id, reviewer_agent_id(固定为后荣的agent id), acceptance_result(pass/fail), problem_details, review_dimensions(JSON), score(0-100), created_at
   * score字段说明：score = Σ(维度_i得分 × 权重_i) / Σ(权重_i)，默认各维度权重均等。review_dimensions JSON中存储各维度的名称、量化标准、实际得分、合格阈值和是否达标。score为所有维度得分的算术平均值（0-100）。

9. **groups** - 群组表（项目讨论群）
   
   * id, project_id, name, description, mode, host_agent_id, created_at

10. **group_members** - 群组-成员关联表
    
    * id, group_id(FK→groups.id), user_id(FK→users.id), agent_id(FK→agents.id), member_type(user/agent), joined_at, role_in_group
    * user_id和agent_id二选一必填：成员为人类用户时user_id必填且agent_id为空，成员为Agent时agent_id必填且user_id为空；member_type标识成员类型

11. **group_messages** - 群聊消息表
    
    * id, group_id, sender_id, sender_type(user/agent), role, content, timestamp, is_streaming, metadata(JSON)

12. **meeting_outcomes** - 会议结果表
    
    * id, group_id, meeting_topic, host_agent_id, started_at, ended_at, minutes, decisions(JSON), todos(JSON), risks(JSON), open_issues(JSON)

13. **swarms** - Agent蜂群表
    
    * id, project_id, manager_agent_id(后发/后达), purpose(code_writing/test), status, created_at

14. **swarm_members** - 蜂群-成员关联表
    
    * id, swarm_id(FK→swarms.id), agent_name, agent_type, registered_at, status

15. **notifications** - 通知表
    
    * id, user_id, project_id, content, type, is_read, created_at

#### 代码仓库相关表

1. **repos** - 代码仓库表
   
   * id, project_id, gitea_repo_id, name, url, ssh_url, http_url, default_branch, is_private, created_at

2. **repo_branches** - 分支表
   
   * id, repo_id, name, commit_sha, is_protected, created_at

3. **pull_requests** - PR表
   
   * id, repo_id, number, title, description, source_branch, target_branch, author, status, created_at, merged_at

4. **commits** - 提交记录表
   
   * id, repo_id, sha, message, author, created_at

5. **task_commits** - 任务与提交关联表
   
   * id, task_id, commit_id, created_at

## 8. 验收标准

### 8.1 16步流程验收

#### 8.1.1 第一步验收：项目创建

* [ ] 人类用户可创建项目并提交初始需求
* [ ] 项目创建后自动在Gitea中创建代码仓库
* [ ] 生成唯一项目ID
* [ ] 自动创建项目文件夹（路径 `/DevFlow/projects/{project_id}/`，含标准子目录结构）
* [ ] 支持富文本/Markdown需求描述，支持附件上传
* [ ] 第一步由人类用户执行，无需QA门控检验

#### 8.1.2 第二步验收：核心目标确认与组织架构搭建

* [ ] 海梅作为默认Hermes Agent主动与人类用户对话
* [ ] 确认软件项目核心目标（经用户确认）
* [ ] 搭建项目组织架构（9个命名Agent角色全部激活）
* [ ] 建立项目讨论群，所有9个命名Agent角色（海梅、后兴、后旺、后发、后达、后富、后贵、后荣、后华）全部加入
* [ ] 后荣检验核心目标和组织架构合格（目标明确性≥80分且组织完整性100%，详见4.3.1节量化打分标准）
* [ ] 检验合格产出已提交到代码库

#### 8.1.3 第三步验收：需求分析

* [ ] 海梅安排后兴与用户对话沟通需求
* [ ] 复杂项目（功能>20项或技术栈>3种或周期>2周或用户要求）在讨论群中召开需求评审会议
* [ ] 生成完整、准确的软件需求说明书
* [ ] 后荣检验需求说明书的完整性达标（12项必查内容，完整性得分≥90分，计算方法：存在项数/12×100）
* [ ] 后荣检验需求说明书的一致性达标（6类矛盾检查，矛盾项总数=0）
* [ ] 后荣检验需求说明书的可验证性达标（7条判定规则，可验证性得分≥90分，计算方法：达标规则数/7×100）
* [ ] 后荣检验需求说明书的无歧义性达标（5类模糊表述检查，模糊表述总数=0，术语表完整性≥95%）
* [ ] 综合评分≥85分
* [ ] 检验合格的需求说明书已提交到代码库
* [ ] 需求说明书保存在项目文件夹的 `docs/` 子目录下

#### 8.1.4 第四步验收：架构设计

* [ ] 海梅安排后旺依据核心目标和需求说明书进行设计
* [ ] 架构设计文档生成并经后荣逐项检验合格
* [ ] 后端设计文档生成并经后荣逐项检验合格
* [ ] 前端设计文档生成并经后荣逐项检验合格
* [ ] 数据库设计文档生成并经后荣逐项检验合格
* [ ] 全部设计文档已提交到代码库

#### 8.1.5 第五步验收：开发环境搭建

* [ ] 海梅安排后富建立开发环境
* [ ] 开发环境可正常运行（代码仓库初始化、框架搭建、依赖配置、数据库初始化）
* [ ] 后荣检验开发环境合格（可用性、配置正确性、依赖完整性）

#### 8.1.6 第六步验收：TDD测试用例计划

* [ ] 海梅依据需求说明书和设计文档制订《TDD测试用例编写计划》
* [ ] 每个测试用例是最小原子化的（单一功能、<200行、单用例、<2小时）
* [ ] 每个测试用例有明确的、可量化的验收标准
* [ ] 后荣检验计划合格（覆盖率≥95%、原子化符合率≥90%、可量化比例≥90%）
* [ ] 检验合格的计划已提交到代码库

#### 8.1.7 第七步验收：TDD测试用例编写

* [ ] 海梅安排后发建立Agent蜂群
* [ ] 蜂群Agent成功完成TDD测试用例编写
* [ ] 后发负责任务分发、进度监控、成果收集
* [ ] 后荣逐用例检验合格（编译通过率=100%、覆盖率≥95%、原子化符合率≥90%、验收标准匹配率≥95%）
* [ ] 检验合格的测试用例全部提交到代码库

#### 8.1.8 第八步验收：代码编写计划

* [ ] 海梅依据需求说明书、设计文档和TDD测试用例计划制订《代码编写计划》
* [ ] 每个代码编写任务是最小原子化的
* [ ] 每个任务有测试用例一一对应
* [ ] 任务依赖关系正确，已画出任务依赖图（有向无环图，无循环依赖）
* [ ] 后荣检验计划合格（任务原子化符合率≥90%、测试用例对应率=100%、循环依赖=0）
* [ ] 检验合格的计划已提交到代码库

#### 8.1.9 第九步验收：功能代码编写

* [ ] 海梅安排后发建立Agent蜂群
* [ ] 蜂群Agent严格按依赖图顺序完成代码编写
* [ ] 每个子任务经后荣逐任务检验合格
* [ ] 有依赖关系的任务，前置任务验收通过后才执行后继任务
* [ ] 前后两个任务由不同的蜂群Agent执行
* [ ] 代码正确性：编译通过率=100%、静态扫描Critical/High=0
* [ ] 测试通过率≥95%
* [ ] 需求匹配度≥90%
* [ ] 检验合格的代码全部提交到代码库

#### 8.1.10 第十步验收：测试环境部署

* [ ] 海梅安排后富部署到测试环境
* [ ] 测试环境部署成功，应用可正常访问
* [ ] 后荣检验合格（环境可用性=100%、应用可访问率=100%、功能可用率≥95%）
* [ ] 检验合格的部署配置已提交到代码库

#### 8.1.11 第十一步验收：全面测试

* [ ] 海梅安排后达建立测试Agent蜂群
* [ ] 单元测试执行完成
* [ ] 模块测试执行完成
* [ ] 集成测试执行完成
