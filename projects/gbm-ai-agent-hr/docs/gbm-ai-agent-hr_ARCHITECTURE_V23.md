## 1. 架构概述

### 1.1 设计目标

GBM AI Agent HR 系统采用 **模块化单体 (Modular Monolith)** 架构，以 AI Agent 为系统核心执行主体，实现人力资源管理全流程的自动化。架构设计遵循以下原则：

1. **零操作性原则** — 所有操作性事务由 Agent 自主完成，人类仅承担审核与仲裁
2. **模块化单体** — 按业务域划分为独立模块（用户中心、招聘培训、薪酬考勤、分析自动化），通过包边界隔离，共享同一进程和数据库，后期可按需拆分为微服务
3. **事件驱动** — 模块内通过 Spring Event 异步通信，跨进程通过 Redis Stream 可靠传递事件
4. **配置驱动** — 业务规则（薪资、考勤、筛选权重）以配置形式管理，Nacos Config 支持热更新
5. **可观测性** — 完整的链路追踪（OpenTelemetry）、日志、监控
6. **弹性容错** — 通过 Resilience4j 实现熔断、限流、重试机制

> **V23 跨文档一致性声明：** 本文档为 GBM AI Agent HR 系统的权威架构设计文档。所有后端设计文档、前端设计文档、数据库设计文档必须与本文档中的架构模式、技术选型、端口分配、编码规范保持一致。任何偏离本文档的设计决策必须经过架构评审。

## 2. 分层架构设计

### 2.1 展示层 (Presentation Layer)

展示层负责用户交互界面和消息推送，包含以下组件：

| 组件 | 技术选型 | 职责 |
|------|----------|------|
| Web 应用 | React 18.x + Ant Design 5.x | HR 审核面板、数据查看、报表展示 |
| PWA/移动端 | workbox 7.x + PWA | 移动端审核、通知接收、扫码入口 |
| 扫码入口 | H5 (React 18) | 面试签到、培训签到、访客登记 |
| 通知推送 | WebSocket + STOMP | 实时推送（Dashboard 待办提醒、Agent 状态更新） |

> **V23 跨文档一致性声明：** 以上前端技术选型为跨文档统一标准，与前端设计文档 V17 保持一致。前端设计文档采用以下技术栈：
> - Web 前端：React 18.x + Ant Design 5.x
> - 状态管理：Zustand 4.x + @tanstack/react-query 5.x
> - HTTP 客户端：Axios 1.x
> - 移动端：PWA + workbox 7.x
> - 构建工具：Vite 5.x
> - 路由：React Router 6.x
> - 国际化：i18next + react-i18next
> - 图表：ECharts 5.x
> - 测试：Vitest + Testing Library

**设计说明：** 展示层仅提供"查看"和"审核"功能，不提供操作性功能。所有数据录入、资料整理、表单填写等操作均由 Agent 完成。

### 2.2 网关层 (Gateway Layer)

K8s Nginx Ingress Controller 作为 L7 网关，处理 SSL 终止、路由转发、静态资源服务。Nacos Config 仅用于配置热更新，不使用服务发现/负载均衡等功能。

> **V23 跨文档一致性声明：** K8s Nginx Ingress Controller 为 L7 网关方案。Spring Cloud Alibaba Nacos Config 仅用于配置热更新（`@NacosValue` / `@RefreshScope`），明确不使用 Spring Cloud 的服务治理功能（网关、服务发现、负载均衡等）。后端设计文档不得引入 Spring Cloud Gateway、Eureka、OpenFeign 等服务治理组件。

```
                    互联网
                      |
              +-------+-------+
              |  K8s Ingress  |
              |  Controller   |
              +---------------+
                      |
              +-------+-------+
              |  主服务 :8080  |
              |  (Modular     |
              |   Monolith)   |
              +---------------+
              |               |
    +---------+         +-----+--------+
    | Python 子服务 |     | Python 子服务|
    | RPA :8090   |     | OCR :8091    |
    +-------------+     +--------------+
```

**职责划分：**
- SSL 证书终止、路由转发、静态资源服务由 Nginx Ingress 处理
- Nacos Config 提供配置热更新能力（`@NacosValue` / `@RefreshScope`）
- 鉴权（JWT 验证）、限流、请求日志由主服务内部处理
- 明确不引入的 Spring Cloud 依赖：Gateway、Eureka、OpenFeign、Nacos Discovery、LoadBalancer

### 2.3 编排调度层 (Orchestration Layer)

```
+---------------------------------------------------------------+
|                    Flowable 7.0.x                             |
|  +------------------+  +------------------+  +--------------+ |
|  | BPMN 流程定义    |  | 并行网关 (Parallel)|  | 排他网关     | |
|  | (招聘流程、入职   |  |  (证件识别并行     |  | (审核/驳回)  | |
|  |   流程、离职流程) |  |    人脸比对等)    |  |              | |
|  +------------------+  +------------------+  +--------------+ |
|  +---------------------------------------------------------+ |
|  |  事件总线 — Spring Event (进程内) + Redis Stream (跨进程) | |
|  |  任务类型：简历筛选、证件识别、薪资计算、RPA 操作等        | |
|  +---------------------------------------------------------+ |
+---------------------------------------------------------------+
```

> **V23 跨文档一致性声明：** Flowable 7.0.x 为流程引擎方案，与后端设计文档 V31 保持一致。Flowable 与 Camunda 8/Zeebe 的 API 和部署方式完全不同，不可互换。Flowable 7.0.x 与 Spring Boot 3.2.x 已确认兼容。

**核心组件：**

1. **流程定义引擎 (Flowable 7.0.x)**
   - 基于 BPMN 2.0 标准定义业务流程
   - 支持并行网关（如证件识别并行执行）、排他网关（审核通过/驳回）
   - 流程版本管理，支持灰度发布

2. **任务分解器 (Task Decomposer)**
   - 将复杂任务（如"入职办理"）分解为子任务
   - 子任务映射到对应的 Agent
   - 支持任务优先级和依赖关系管理

3. **状态管理器 (State Manager)**
   - Redis 存储流程实例状态（TTL = 30 天）
   - MySQL 持久化流程历史（用于审计和追溯）
   - 支持断点恢复：Agent 失败后可从上一个检查点继续

### 2.4 域模块层 (Domain Modules)

模块化单体架构下，4 个业务模块是系统的核心业务执行层，各模块通过包边界隔离，共享同一 JVM 进程。

#### 2.4.1 链路追踪设计

全系统采用 OpenTelemetry 进行分布式链路追踪：

```
User Request → Ingress → [TraceID] → 主服务 :8080 → [SpanID] →
  → Spring Event / Redis Stream → [TraceID] → Python 子服务 → [SpanID]
```

| 组件 | 追踪方式 | 实现 |
|------|----------|------|
| HTTP 请求 | W3C Trace Context 头 | OpenTelemetry Java Agent |
| Redis Stream 消息 | 消息头注入 TraceContext | 自定义拦截器 |
| 数据库查询 | SQL 查询 Span | OpenTelemetry JDBC Instrumentation |
| Agent 任务 | 自定义 Span | Flowable 原生 Trace ID 集成 |
| Python 子服务调用 | HTTP 头传递 TraceContext | WebClient 拦截器 |

**链路追踪数据存储：** Jaeger (All-in-one 模式，单节点部署)

### 2.5 共享基础设施层 (Shared Infrastructure)

| 服务 | 端口 | 职责 | 技术选型 |
|------|------|------|----------|
| RPA 子服务 | 8090 | 社保局、公积金网站自动化操作 | Playwright Python |
| OCR 子服务 | 8091 | 身份证、学历证、银行卡识别 | PaddleOCR Python |

**RPO/RTO 保障方案 (2.6.1)：**

| 模型服务 | RPO (数据丢失) | RTO (恢复时间) | 保障措施 |
|----------|----------------|----------------|----------|
| vLLM | 模型权重不丢失（只读） | < 30 分钟 | Docker 容器重启 + 模型缓存预热 |
| PaddleOCR | 不丢失（只读模型） | < 15 分钟 | 容器重启即恢复 |
| face_recognition | 不丢失（只读模型） | < 15 分钟 | 容器重启即恢复 |
| bge-m3 | 不丢失（只读模型） | < 10 分钟 | 容器重启即恢复 |

**Milvus 单节点 RPO/RTO 保障方案 (2.6.2)：**

由于向量数据（简历嵌入、文档嵌入等）属于可重建数据，Milvus 单节点采用以下备份和恢复策略：

| 指标 | 目标值 | 说明 |
|------|--------|------|
| RPO | < 24 小时 | 每日备份，最多丢失 24 小时向量数据 |
| RTO | < 4 小时 | 从备份恢复 + 数据重建 |

**备份执行细节：**

```bash
# 每日凌晨 2:00 执行 Milvus 快照备份
milvusctl snapshot create -c default_collection -u http://milvus:19530

# 备份存储至 MinIO
mc cp milvus_snapshots/ minio/milvus-backups/$(date +%Y%m%d)/ --recursive

# 完整性校验
milvusctl snapshot verify -p minio/milvus-backups/$(date +%Y%m%d)/
```

**恢复步骤详解（5 步流程）：**

| 步骤 | 操作 | 预计耗时 |
|------|------|----------|
| 1 | 停止 Milvus 服务 | < 1 分钟 |
| 2 | 从 MinIO 拉取最新快照 | 5-10 分钟（取决于数据量） |
| 3 | 执行快照恢复命令 `milvusctl snapshot restore` | 10-30 分钟 |
| 4 | 启动 Milvus 服务并验证集合完整性 | < 5 分钟 |
| 5 | 对缺失的向量数据进行增量重建（从 MySQL 源数据重新 embedding） | 1-2 小时 |

**数据丢失影响评估：**

| 影响维度 | 影响程度 | 说明 |
|----------|----------|------|
| 核心业务 | 无影响 | 简历原文、员工数据存储在 MySQL，不受 Milvus 故障影响 |
| 检索功能 | 暂时不可用 | 语义搜索、简历推荐功能暂停，待恢复后可用 |
| 重建耗时 | 2-4 小时 | 从 MySQL 源数据重新生成 embedding 向量 |

## 6. 关键设计决策

### 6.1 模块化单体架构决策 (V23 修订)

**决策：** 采用模块化单体 (Modular Monolith) 架构，主服务单端口 8080。

**背景：** V15 架构将 8 个 Agent 服务合并为 4 个域服务并采用微服务架构（端口 8081~8084），但实际实施中发现以下问题：
1. 模块化单体更适合当前规模（250 并发用户），避免微服务过度拆分带来的运维复杂度
2. 包边界隔离已能满足模块独立性需求
3. 共享数据库连接池减少资源消耗
4. 后期可按需拆分为微服务

**模块划分：**

| 模块 | 包路径 | 职责 |
|------|--------|------|
| 用户中心模块 | gbm-hr-user | 员工管理、入职、离职、证书、证明 |
| 招聘培训模块 | gbm-hr-recruit | 简历筛选、面试、培训管理 |
| 薪酬考勤模块 | gbm-hr-payroll | 考勤、薪资、绩效、外务 |
| 分析自动化模块 | gbm-hr-auto | 报表、审核、洞察、流程优化 |
| 认证授权模块 | gbm-hr-auth | 认证、授权、JWT 管理 |

**影响评估：**
- 正面：减少部署复杂度、降低跨服务调用开销、简化数据一致性管理
- 负面：单进程故障影响全部模块（通过多副本部署缓解）

> **V23 跨文档一致性声明：** 系统采用模块化单体 (Modular Monolith) 架构，主服务单端口 8080，与后端设计文档 V31 保持一致。

### 6.2 Nginx Ingress + Nacos Config 方案 (V23 修订)

**决策：** K8s Nginx Ingress Controller 作为 L7 网关，Nacos Config 仅用于配置热更新。

**背景：** 模块化单体架构下不需要 Spring Cloud 的服务治理功能（网关、服务发现、负载均衡等），但需要配置热更新能力。

**Nacos 配置管理的具体依赖：**

| 依赖 | 版本 | 说明 |
|------|------|------|
| `spring-cloud-starter-alibaba-nacos-config` | 2023.0.0.0 | Nacos 配置管理（提供 `@NacosValue`、`@RefreshScope` 注解） |
| `nacos-client` | 2.x | Nacos 客户端（由上述 starter 传递依赖引入） |

**明确不引入的 Spring Cloud 依赖：**

| 依赖 | 原因 |
|------|------|
| `spring-cloud-starter-gateway` | 模块化单体不需要 API 网关 |
| `spring-cloud-starter-netflix-eureka-client` | 不需要服务注册发现 |
| `spring-cloud-starter-openfeign` | 模块间通过包内方法调用，不需要 Feign |
| `spring-cloud-starter-alibaba-nacos-discovery` | 不需要服务发现 |
| `spring-cloud-starter-loadbalancer` | 不需要客户端负载均衡 |

> **V23 跨文档一致性声明：** Nacos 仅使用配置热更新能力（`@NacosValue` / `@RefreshScope`），不使用服务发现/负载均衡等功能。

### 6.3 端口分配策略

**决策：** 主服务采用单端口 8080，Python 子服务使用 8090~8092，AI 模型服务使用 8000~8003。

**理由：**
1. 模块化单体只需一个端口，简化网络配置
2. Python 子服务独立端口便于健康检查和故障隔离
3. AI 模型服务使用 800x 端口段，便于区分

### 6.4 本地化 AI 模型部署

**决策：** 所有 AI 模型（LLM、OCR、人脸识别、Embedding）均采用本地部署，不依赖云端 API。

**理由：**
1. **数据安全** — HR 数据包含大量个人信息（身份证、银行卡、薪资等），本地部署确保数据不出域
2. **成本可控** — 一次性硬件投入，无按量付费的不确定性
3. **延迟稳定** — 本地网络延迟 < 1ms，远低于云端 API（通常 50-200ms）
4. **可用性强** — 不依赖外部网络，避免因云端服务故障导致系统不可用

**硬件需求：**
- GPU 服务器：1× NVIDIA A100 (80GB) 用于 LLM 推理
- CPU 服务器：OCR、人脸识别、Embedding 共享一台 16 Core / 64GB RAM 服务器

### 6.5 Milvus 单节点部署

**决策：** 向量数据库 Milvus 采用单节点 Docker Compose 部署，而非集群模式。

**理由：**
1. **数据量评估** — 预计简历向量 < 100 万，文档向量 < 500 万，单节点完全满足
2. **运维简化** — 单节点部署大幅降低运维复杂度
3. **性能足够** — 单节点 Milvus 在 1000 万向量规模下检索延迟 < 100ms
4. **可扩展性** — 未来数据量增长时可平滑迁移至集群模式

**备份策略：** 每日凌晨 2:00 执行快照备份至 MinIO，详见第 2.6.2 节。

### 6.6 弹性容错方案

**决策：** 采用 Resilience4j 实现熔断、限流、超时控制。

**方案组成：**

| 组件 | 职责 | 配置 |
|------|------|------|
| Resilience4j CircuitBreaker | 熔断器 | 每个下游调用独立配置 |
| Resilience4j RateLimiter | 限流器 | 防止下游过载 |
| Resilience4j Retry | 重试机制 | 指数退避策略 |
| Resilience4j Timeout | 超时控制 | 快速失败机制 |

**熔断策略：**

| 指标 | 阈值 | 动作 |
|------|------|------|
| 错误率 | > 50% (10 秒窗口) | 打开熔断器，停止调用 30 秒 |
| 慢调用率 | > 80% (P95 > 2 秒) | 降级为缓存数据或默认值 |
| 调用超时 | > 5 秒 | 快速失败，记录日志 |

## 7. 分布式事务与数据一致性

### 7.1 事务场景分析

GBM AI Agent HR 系统存在以下跨模块事务场景：

| 场景 | 涉及模块 | 一致性要求 | 说明 |
|------|----------|------------|------|
| 新员工入职 | 招聘培训 → 用户中心 → 薪酬考勤 | 最终一致性 | 招聘完成后创建员工档案，然后初始化薪资信息 |
| 薪资发放 | 薪酬考勤 → 用户中心 | 强一致性 | 薪资计算结果与员工银行账户信息必须一致 |
| 证书更新 | 用户中心 → 招聘培训 | 最终一致性 | 证书更新后同步到培训记录 |
| 离职流程 | 用户中心 → 薪酬考勤 → 招聘培训 | 最终一致性 | 离职后停薪、归档培训记录、释放招聘名额 |

### 7.2 事务方案选型

**决策：** 采用 Saga 模式（编排式）作为主要的分布式事务方案。

**选型对比：**

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| Saga (编排式) | 中心化控制、易于追踪、补偿逻辑清晰 | 编排器成为单点 | 本系统主方案 |
| 本地消息表 | 实现简单 | 需要额外定时任务清理 | 非关键场景备用 |
| TCC | 强一致性 | 侵入业务代码、实现复杂 | 薪资发放（见 7.3 节） |

### 7.3 Saga 编排设计

**编排器：** Flowable 7.0.x 作为 Saga 编排器，利用 BPMN 流程定义事务步骤和补偿逻辑。

```
[招聘完成] → [创建员工档案] → [初始化薪资] → [发送通知]
     │              │              │              │
     │              ↓              ↓              ↓
     │         [补偿:删除档案] [补偿:重置薪资] [无需补偿]
     ↓
[补偿:撤销招聘]
```

**补偿策略：**

| 步骤 | 正常操作 | 补偿操作 | 补偿失败处理 |
|------|----------|----------|-------------|
| 创建员工档案 | 插入员工记录 | 标记为"待删除"（软删除） | 记录告警，人工介入 |
| 初始化薪资 | 插入薪资配置 | 删除薪资配置 | 记录告警，人工介入 |
| 发送通知 | 发送入职通知 | 发送取消通知 | 忽略（通知可重复） |

### 7.4 TCC 方案（薪资发放场景）

**决策：** 薪资发放场景采用 TCC (Try-Confirm-Cancel) 模式，确保强一致性。

**TCC 三阶段：**

| 阶段 | 操作 | 说明 |
|------|------|------|
| Try | 冻结薪资金额、锁定银行账户 | 预留资源，不实际转账 |
| Confirm | 执行转账、更新薪资记录 | 实际执行操作 |
| Cancel | 解冻薪资金额、释放银行账户 | 回滚预留资源 |

### 7.5 数据一致性保障

| 保障措施 | 实现方式 | 说明 |
|----------|----------|------|
| 幂等性 | 请求 ID 去重表 | 每个操作携带唯一请求 ID，防止重复执行 |
| 对账机制 | 定时对账任务 | 每日凌晨对账，发现不一致自动修复 |
| 审计日志 | 操作日志表 | 记录所有数据变更，支持追溯和修复 |
| 数据校验 | 入库前校验 | 关键数据（薪资、社保）入库前多重校验 |

## 12. Agent 异常处理与补偿机制

### 12.1 异常分类

| 异常类型 | 说明 | 示例 | 处理策略 |
|----------|------|------|----------|
| 临时性异常 | 网络抖动、服务短暂不可用 | HTTP 503、数据库连接超时 | 自动重试（指数退避） |
| 永久性异常 | 数据不存在、权限不足 | HTTP 404、403 | 记录日志，通知人工 |
| 业务异常 | 业务规则不满足 | 薪资计算结果为负数 | 记录日志，触发补偿 |
| 外部系统异常 | 外部 API 不可用、RPA 目标网站变化 | 社保局网站维护 | 降级处理，定时重试 |
| AI 推理异常 | LLM 返回结果不符合预期 | OCR 识别失败 | 重试或降级至人工 |

### 12.2 重试策略

**决策：** 采用 Resilience4j Retry 实现智能重试。

| 异常类型 | 重试次数 | 退避策略 | 最大等待时间 |
|----------|----------|----------|-------------|
| 网络超时 | 3 次 | 指数退避 (1s, 2s, 4s) | 10 秒 |
| HTTP 5xx | 3 次 | 固定间隔 (2s) | 8 秒 |
| 数据库连接 | 5 次 | 指数退避 (0.5s, 1s, 2s, 4s, 8s) | 20 秒 |
| AI 推理 | 2 次 | 固定间隔 (5s) | 10 秒 |
| RPA 操作 | 3 次 | 固定间隔 (10s) | 30 秒 |

### 12.3 熔断策略

**决策：** 采用 Resilience4j CircuitBreaker 实现服务熔断。

| 下游服务 | 错误率阈值 | 滑动窗口 | 熔断持续时间 | 半开状态最大调用 |
|----------|-----------|----------|-------------|-----------------|
| OCR 服务 | 50% | 100 次 | 30 秒 | 5 次 |
| RPA 服务 | 30% | 50 次 | 60 秒 | 3 次 |
| LLM 服务 | 40% | 100 次 | 30 秒 | 5 次 |
| 人脸识别 | 50% | 100 次 | 30 秒 | 5 次 |
| 数据库 | 20% | 50 次 | 60 秒 | 3 次 |

### 12.4 补偿机制

**决策：** Saga 补偿 + 死信队列双重保障。

**Saga 补偿流程：**

```
[任务 A 成功] → [任务 B 成功] → [任务 C 失败]
                                      ↓
                               [执行 C 补偿]
                                      ↓
                               [执行 B 补偿]
                                      ↓
                               [执行 A 补偿]
                                      ↓
                               [记录补偿结果]
                               [通知人工介入（如补偿失败）]
```

**死信队列 (DLQ) 设计：**

| 队列 | 用途 | 处理策略 |
|------|------|----------|
| dlq.user-module | 用户中心模块失败消息 | 每小时重试，3 次后转人工 |
| dlq.recruit-module | 招聘培训模块失败消息 | 每小时重试，3 次后转人工 |
| dlq.payroll-module | 薪酬考勤模块失败消息 | 每小时重试，3 次后转人工 |
| dlq.auto-module | 分析自动化模块失败消息 | 每小时重试，3 次后转人工 |

### 12.5 降级模式

**决策：** 当外部依赖不可用时，系统进入降级模式保障核心业务。

| 降级场景 | 降级策略 | 影响范围 |
|----------|----------|----------|
| LLM 服务不可用 | 使用规则引擎替代 AI 推理 | 简历筛选降级为关键词匹配 |
| OCR 服务不可用 | 暂停证件自动识别，允许后续补录 | 入职办理延迟，但不阻塞 |
| RPA 服务不可用 | 暂停外务自动操作，生成待办清单 | 社保/公积金操作延迟 |
| 人脸服务不可用 | 暂停人脸比对，使用证件号校验 | 签到功能降级 |
| 向量检索不可用 | 使用关键词检索替代 | 简历推荐精度下降 |

**降级例外条款（与 SRS 8.3 节一致）：**
- 降级期间的所有人工操作需完整记录至审计日志
- 降级原因和持续时间需纳入月度运维报告
- 降级因素消除后应立即恢复全自动化模式

### 12.6 告警机制

| 告警级别 | 触发条件 | 通知方式 | 响应时间 |
|----------|----------|----------|----------|
| P0 (紧急) | 核心服务不可用、数据丢失 | 电话 + 短信 + 邮件 | 15 分钟内 |
| P1 (高) | 服务性能下降 > 50%、熔断触发 | 短信 + 邮件 | 30 分钟内 |
| P2 (中) | 重试次数超限、死信队列积压 | 邮件 + 钉钉/企微 | 2 小时内 |
| P3 (低) | 常规异常、日志警告 | 邮件 | 24 小时内 |

## 13. 多租户隔离策略

### 13.1 多租户需求分析

**决策：** GBM AI Agent HR 系统当前为单租户部署，但架构设计预留多租户扩展能力。

**理由：**
1. GBM 为单一企业部署，当前无需多租户
2. 未来可能扩展为 SaaS 模式服务于多家企业
3. 预留多租户能力可降低未来改造成本

### 13.2 多租户架构设计（预留方案）

**隔离级别：** 数据库 Schema 隔离（逻辑隔离）

| 隔离级别 | 实现方式 | 优点 | 缺点 | 适用场景 |
|----------|----------|------|------|----------|
| 数据库隔离 | 每个租户独立数据库 | 最高隔离性 | 成本高 | 高端 SaaS |
| Schema 隔离 | 每个租户独立 Schema | 较高隔离性 | 中等成本 | 本系统预留方案 |
| 字段隔离 | 共享表，tenant_id 字段区分 | 成本最低 | 隔离性弱 | 低端 SaaS |

### 13.3 租户标识设计

**租户 ID 规则：** `TENANT` + `6 位数字`

| 租户 | 租户 ID | 说明 |
|------|---------|------|
| GBM (当前) | TENANT000001 | 默认租户 |

**实现方式：**

| 组件 | 实现 |
|------|------|
| 请求识别 | HTTP 头 `X-Tenant-ID` |
| 数据库路由 | MyBatis-Plus 插件自动注入 tenant_id |
| 缓存隔离 | Redis Key 前缀 `tenant:{tenant_id}:` |
| 文件隔离 | MinIO 路径 `/tenants/{tenant_id}/` |

### 13.4 租户数据迁移方案

| 场景 | 迁移方式 | 说明 |
|------|----------|------|
| 新增租户 | 自动创建 Schema + 初始化数据 | 部署脚本自动执行 |
| 租户数据导出 | 全量导出为 SQL + 文件包 | 用于备份或迁移 |
| 租户删除 | 软删除（标记为禁用） | 保留数据 30 天后可恢复 |

## 14. Agent 间通信机制

### 14.1 通信方式

| 通信方式 | 使用场景 | 协议 | 说明 |
|----------|----------|------|------|
| 包内方法调用 | 模块间同步调用 | 方法调用 | 模块化单体内优先方式 |
| Spring Event | 模块内事件通知 | 进程内发布-订阅 | 异步解耦 |
| Redis Stream | 跨进程事件传递 | Redis Stream | at-least-once 投递 |
| HTTP API | 主服务调用 Python 子服务 | HTTP/REST (WebClient) | OCR、RPA、人脸服务 |

### 14.2 包内方法调用设计

**决策：** 模块化单体内模块间优先通过包内方法调用（InternalApi 模式 + DTO 传递）。

**调用规范：**

| 规范项 | 规则 |
|--------|------|
| 调用方式 | 包内方法调用，通过 Spring Bean 注入 |
| 数据传输 | DTO 对象传递 |
| 事务管理 | @Transactional 注解管理事务边界 |
| 超时控制 | 不适用（进程内调用） |

### 14.3 异步消息设计

**决策：** 采用 Spring Event（进程内）+ Redis Stream（跨进程）作为异步消息机制。

**Spring Event 事件类型：**

| 事件类型 | 用途 | 说明 |
|----------|------|------|
| EmployeeCreatedEvent | 员工创建事件 | 招聘完成后触发 |
| SalaryCalculatedEvent | 薪资计算完成事件 | 薪资核算完成后触发 |
| AttendanceRecordedEvent | 考勤记录事件 | 打卡完成后触发 |
| TrainingCompletedEvent | 培训完成事件 | 培训结束后触发 |

**Redis Stream 设计：**

| 流名称 | 用途 | 消费者组 | 保留策略 |
|--------|------|----------|----------|
| hr:employee:events | 员工事件 | user-module-group | 30 天 |
| hr:payroll:events | 薪资事件 | payroll-module-group | 30 天 |
| hr:attendance:events | 考勤事件 | payroll-module-group | 7 天 |
| hr:training:events | 培训事件 | recruit-module-group | 30 天 |

**消息格式：**

```json
{
  "event_id": "evt_20260615_001",
  "event_type": "employee.onboarded",
  "timestamp": "2026-06-15T10:30:00Z",
  "source_module": "gbm-hr-recruit",
  "data": {
    "emp_no": "EMP20260001",
    "emp_name": "张三",
    "dept_code": "DEPT001",
    "entry_date": "2026-06-15"
  }
}
```

> **V23 跨文档一致性声明：** 消息格式中 dept_code 字段采用 DEPT001 格式（无连字符），与第 11.2 节部门编码规则保持一致。所有事件消息、REST API 请求/响应中的部门编码均须统一使用此格式。

### 14.4 消息可靠性保障

| 保障措施 | 实现方式 |
|----------|----------|
| 生产端确认 | Redis Stream XACK 确认机制 |
| 消费端确认 | StreamListener 模式，处理完成后手动 ACK |
| 消息顺序 | 同一员工消息使用 emp_no 作为分组键 |
| 死信队列 | 消费失败 3 次后转入 DLQ |
| 消息追踪 | 消息头注入 TraceContext |
| 容量管理 | Redis Stream 设置 MAXLEN 限制，防止无限增长 |

## 15. 跨服务数据流设计

### 15.1 核心数据流

**1. 新员工入职数据流：**

```
[招聘培训模块] ──Spring Event──→ [用户中心模块]
                                      ↓
                              1. 创建员工档案
                              2. 初始化个人信息
                              3. 分配员工编号
                                      ↓
                              [用户中心模块] 发布员工创建事件
                                      ↓
                              [Redis Stream: hr:employee:events]
                                      ↓
                              [薪酬考勤模块] 消费事件
                                      ↓
                              1. 初始化薪资配置
                              2. 设置社保/公积金账户
                                      ↓
                              [薪酬考勤模块] 发布薪资初始化事件
                                      ↓
                              [Redis Stream: hr:payroll:events]
                                      ↓
                              [分析自动化模块] 消费事件
                                      ↓
                              更新招聘效果统计数据
```

**2. 薪资发放数据流：**

```
[薪酬考勤模块] ──薪资计算完成──→ [Redis Stream: hr:payroll:events]
                                      ↓
                             [薪酬考勤模块] 内部 TCC 事务
                                      ↓
                             1. Try: 冻结薪资金额
                             2. Confirm: 执行转账
                             3. 发布发放完成事件
                                      ↓
                             [Redis Stream: hr:payroll:events]
                                      ↓
                             [用户中心模块] 消费事件
                                      ↓
                             更新员工薪资记录
                                      ↓
                             [分析自动化模块] 消费事件
                                      ↓
                             更新财务报表
```

**3. 离职流程数据流：**

```
[用户中心模块] ──离职申请──→ [Redis Stream: hr:employee:events]
                                 ↓
                        [用户中心模块] 启动离职流程
                                 ↓
                        1. 生成交接清单
                        2. 通知相关部门
                                 ↓
                        [用户中心模块] 发布离职进行中事件
                                 ↓
                        [Redis Stream: hr:employee:events]
                                 ↓
                        [薪酬考勤模块] 消费事件
                                 ↓
                        1. 计算最后薪资
                        2. 停止社保/公积金
                                 ↓
                        [招聘培训模块] 消费事件
                                 ↓
                        1. 归档培训记录
                        2. 释放招聘名额
                                 ↓
                        [用户中心模块] 完成离职
                                 ↓
                        1. 更新员工状态
                        2. 归档员工档案
```

### 15.2 数据流监控

| 监控指标 | 监控方式 | 告警阈值 |
|----------|----------|----------|
| Redis Stream 积压 | Consumer Group Pending 数 | 单消费者组 > 10 万条 |
| 处理延迟 | 消息时间戳 vs 处理时间戳 | P95 > 5 秒 |
| 处理失败率 | 失败消息数 / 总消息数 | > 1% |
| 数据一致性 | 定时对账任务 | 差异 > 0 |

### 15.3 数据流幂等性

| 场景 | 幂等键 | 实现方式 |
|------|--------|----------|
| 员工创建 | emp_no | 唯一索引 + 请求 ID 去重表 |
| 薪资发放 | salary_batch_no | 批次号唯一索引 |
| 考勤记录 | emp_no + date + type | 复合唯一索引 |
| 培训签到 | training_no + emp_no | 复合唯一索引 |
