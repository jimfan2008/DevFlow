## 1. 引言

### 1.1 编写目的

本文档定义 GBM AI Agent HR 智能人力管理系统的完整需求规格。本系统是**彻底的 AI 原生系统**——所有可操作性事务均由 AI Agent 自主执行，人类用户（人事专员、部门主管、外务专员等）的职责仅限于战略性审核、争议仲裁和政策制定，不再承担任何操作性工作。本文档作为系统设计、开发、测试和验收的唯一依据。

### 1.2 项目范围

本系统覆盖企业人力资源管理全生命周期，包括但不限于：招聘管理、入职办理、试用期管理、离职管理、培训管理、考勤管理、薪资管理、绩效管理、外务管理（工伤、住房公积金及其他政府申报事务）、员工证明开具等全流程业务。

本系统的核心特征是：**没有任何一项操作性任务需要人工执行**。每一环节的操作均由对应的 AI Agent 自动完成。人类仅在需要最终决策或法律要求的确认场景中行使审核/审批权，不参与任何数据录入、资料整理、表单填写、系统登录等操作性动作。

### 1.3 术语定义

| 术语 | 定义 |
|------|------|
| AI Agent | 具有自主感知（获取数据/文档）、推理（分析问题/做出决策）、行动（操作外部系统/生成内容）和执行（完成操作）能力的智能体。在本系统中，Agent 不仅是辅助工具，而是业务的实际执行主体 |
| AI 原生系统 | 以 AI Agent 为系统架构核心和业务流程驱动力的软件系统。系统不存在独立于 Agent 的"人工操作面板"；所有功能均以 Agent 能力的暴露形式存在 |
| RPA-Agent | 针对无官方 API 的外围系统（如社保局网站、公积金网站），由 AI Agent 驱动的网站自动化代理，模拟人类鼠标点击和键盘输入来完成操作 |
| 战略性审核 | 人类对 AI Agent 输出结果的审阅和确认。审核人无需知晓底层数据的计算过程和整理逻辑，仅需确认结果的可接受性。审核是一种治理行为，而非操作行为的延续 |
| 争议仲裁 | 当出现无法通过规则解决的异常或冲突时，由人类进行的最终裁量 |
| Multi-Modal LLM | 多模态大语言模型，可同时处理文本、图像、语音等多种输入形式，用于证件识别、人脸比对、文档理解等场景 |
| Agent Orchestration Layer | Agent 编排层，负责任务分解、Agent 调度和结果汇聚，是实现端到端自动化的中枢神经系统 |
| Chain-of-Thought Verification | 思维链验证，要求 Agent 在执行关键操作时输出推理过程供人类追溯核查 |
| 零操作性原则 | 系统的核心设计原则：任何可以由机器执行的步骤都不应出现在人工操作清单中 |

## 2. 项目概述

### 2.1 产品背景

企业当前人力资源管理面临以下系统性挑战：

1. 人力资源团队精力大量消耗于简历初筛、资料整理、表单填报、系统操作等重复性劳动
2. 入职流程中证件录入、协议排版、档案管理高度人工依赖，耗时长且易出错
3. 培训管理全流程缺乏自动化工具，签到统计、阅卷评分、资料归集全程依赖人工
4. 考勤统计和薪资核算需要大量手工计算与核对，不仅耗时且出错风险高
5. 外务工作（工伤处理、公积金增减员、社保申报等）涉及多个政府网站的多步操作，耗费大量人工时间
6. 绩效考核数据收集和汇总效率低下
7. 体系审核前的资料归集工作集中在短时间内完成，人力需求陡增
8. 证书证照效期监控依靠人工记忆或手工台账，容易漏管

上述问题的本质是：**HR 团队的精力被大量低附加值操作所占用，而无法聚焦于人才战略和组织发展等高价值工作**。因此，企业决定建设一套彻底 AI 原生的 HR 系统，将全部操作性事务交给 AI Agent，使人资团队的职能得以转型。

### 2.2 AI 原生系统设计原则

本系统遵循以下设计原则，其中每一条都服务于零操作性原则的实现：

1. **零操作性原则** —— 凡是可以由系统自动完成的步骤，绝不给人工操作留口子。人事专员不再有任何"点击按钮""填写表单""登录外部网站""整理文件夹""复制粘贴数据"的操作任务。

2. **Agent-first 架构** —— 系统的每项功能都以 AI Agent 为核心来设计和交付。不存在"先有人工操作再自动化"的路径规划，系统设计之初就假定所有步骤由 Agent 执行。

3. **端到端自主闭环** —— 每个业务流程从触发条件满足那一刻起，到最终结果输出并归档止，整个过程由 Agent 链自动串联完成，中途无需任何人工作业接力。

4. **主动性智能** —— Agent 不只是被动响应查询，而是在适当时机主动执行：在试用期届满前自动发起考核流程、在证书到期前自动发起续约申请、在发现考勤异常时主动标记并上报、在月末主动启动薪资核算。

5. **持续学习与自我优化** —— 系统通过积累的历史数据和人类审核反馈持续改进模型判断精度：简历筛选规则根据每轮面试通过率自动调整权重、薪资核算规则跟随政策变化自动更新。

6. **透明可追溯** —— 每一个 Agent 决策都有完整的推理链记录，人类可随时审查 Agent 做出某项判断的逻辑依据。关键操作需附带思维链（Chain-of-Thought）以供核查。

7. **安全护栏（Guardrails）** —— Agent 在执行可能产生重大影响的操作前设有自动阻断规则：如涉及资金变动、对外发送内容、删除数据等操作需满足预设安全条件方可放行。

8. **分级异常处理** —— 异常按严重程度分级。低级别异常由 Agent 自动纠偏重试；中级别异常标记并由人类在方便时批量审核；高级别异常立即告警，需相关负责人及时处理。

9. **人机协作模式革新** —— 人与系统的关系从"人工操作→系统辅助"转变为"Agent 执行→人类审核"。人类的参与点是"看结果"而非"动手做"。

|------|----------|----------------|

#### 2.4.2 阶段性建设重点

**第一阶段（基础自动化能力建设）：**
- 招聘 Agent：简历自动抓取、智能匹配评分、面试试卷生成、客观题自动阅卷
- 入职 Agent：扫码登录、证件 OCR 识别、人事档案自动生成、人脸建档
- 培训 Agent：扫码签到、自动组卷、阅卷、上岗证生成
- 考勤 Agent：数据汇总、异常识别
- 薪资 Agent：月度薪资自动核算、工资条自动发放
- 绩效 Agent：考核数据收集与汇总

**第二阶段（外务自动化延伸）：**
- 离职 Agent：表单自动生成、离职证明开具
- 外务 Agent：工伤 RPA 自动申报、公积金 RPA 参保/补缴操作
- 证明 Agent：各类证明智能生成
- 教材转视频 Agent：PPT/文档自动生成培训视频

**第三阶段（智能化增强）：**
- 简历库智能管理与人才画像
- 特种作业证书全流程自动监控与续约
- 体系审核一键资料包生成
- 员工证明自助门户
- 薪资预算预测与费用单据 AI 整理
- Agent 自主学习与模型自优化

## 3. 功能需求

### 3.1 招聘管理

#### 3.1.1 人力需求发布与多渠道投放

**功能描述：** 由 Agent 自动完成招聘信息在各渠道的生成和发布。

**输入：**
- 用人需求概要（岗位名称、职级、编制人数、到岗时限）
- 部门主管口头/文本形式的岗位核心要求

**处理规则：**

1. 人事专员在系统录入基本用人需求
2. **招聘 Agent** 自动解析需求，利用 LLM 生成专业化的职位描述
3. **招聘 Agent** 自动分发至前程无忧、中国人才热线等已配置的招聘平台
4. 支持 ATS API 对接或网页端自动化两种方式
5. 信息发布后 Agent 持续监控投递量，如需调剂文案自动建议

**输出：**
- 已发布招聘信息（含各平台 URL）
- 发布信息的时间戳和版本

#### 3.1.2 多平台简历自动筛选与智能分类

**功能描述：** Agent 跨平台抓取简历、智能匹配评分、分类归档全流程自动化。

**输入：**
- 岗位 JD（含学历要求、工作年限、技能清单、年龄要求、证书要求等结构化字段）

**处理规则：**

1. **简历抓取 Agent** 定时（每 15 分钟）从各招聘平台拉取投递数据
2. 自动去重（基于姓名+身份证/手机号+应聘岗位组合判重）
3. **匹配评分 Agent** 对每份简历执行多维度评分：

| 维度 | 权重 | 评分规则 |
|------|------|---------|
| 学历匹配度 | 15% | 按学历等级映射：博士(6)、硕士(5)、本科(4)、大专(3)、高中/中专(2)、初中(1)。等于或高于岗位要求的得 100%，每降一级得 60%，低于两级的得 0% |
| 工作经验匹配度 | 25% | 年限满足岗位要求得满分；未满要求时按比例计分（实际年限÷要求年限×100%）；超出上限同样按比例计但设封顶系数 1.0 |
| 技能匹配度 | 20% | 按技能关键词命中计算：(命中技能数 ÷ 要求技能总数) × 100%，支持同义词/近义技能模糊匹配（由 LLM 判定） |
| 年龄匹配度 | 5% | 在规定区间内得满分，区间外得 0 分。如要求"25-35 岁"，24 岁和 36 岁均为 0 分，25 岁和 35 岁为满分 |
| 证书匹配度 | 15% | 持有所需证书得满分，缺失得 0 分（含特种作业证书、行业资格证） |
| 语义综合匹配度 | 20% | LLM 对简历全文与 JD 进行语义比对，输出 0-100 分语义分；同一份简历重复评分3次，3次结果中最大值与最小值之差应不超过 3 分，以确保一致性和可重复性 |

4. 各维度加权求和得出综合得分（0-100 分）
5. 系统按以下阈值自动分拣：

| 类别 | 分数区间 | Agent 处置 | 是否需要人工干预 |
|------|---------|------------|------------------|
| 高潜简历 | > 合格线 + 10 分 | 自动下载、解析、入库并标记为"强烈推荐" | 否 |
| 候选简历 | 合格线 - 10 分 至 合格线 + 10 分 | 自动入库，提交人事专员审核确认 | 是，仅审核确认 |
| 淘汰简历 | < 合格线 - 10 分 | 自动打淘汰标签，保留记录 | 否 |

6. 系统支持设定合格线（默认 60 分），人事专员可按岗位特性动态调整阈值

7. 每季度对筛选准确性进行评估：以后续面试转化率作为回溯指标，当面试转化率低于基线 80% 时触发 Agent 评分模型权重自检和优化。权重调整触发条件量化标准如下：
   - 当某维度对应的面试淘汰率连续 2 个季度超过 40% 时，该维度权重自动下调 5 个百分点
   - 当某维度对应的面试通过率连续 2 个季度超过 85% 时，该维度权重自动上调 3 个百分点
   - 单次调整幅度不超过 ±5 个百分点，所有维度权重调整后仍须满足总和 = 100%
   - 权重调整后自动产出调整报告提交人事专员确认

**输出：**
- 每份简历的匹配评分、分项得分明细和推理摘要
- 已入库简历和被淘汰简历列表
- 候选简历名单（提交人工审核）

#### 3.1.3 智能面试题生成与组卷

**功能描述：** Agent 根据岗位要求从题库中自主抽题，一键生成差异化试卷并绑定考试二维码。

**输入：**
- 岗位类型/层级
- 考试科目（通用知识/专业技能/管理能力/安全规范等）
- 考生信息

**处理规则：**

1. **组卷 Agent** 按以下规则自动出题：
   - 题量：30-50 题/卷，默认为 40 题
   - 题型比例：单选题 40%±5%、多选题 30%±5%、判断题 30%±5%
   - 难度分布：简单（1-3 分）40%±5%、中等（4-6 分）40%±5%、困难（7-10 分）20%±5%
   - 同岗位同时段任意两份试卷重合题目≤30%
   - Agent 可根据岗位特点动态调整（如安全管理岗位可提高安全相关题目的比重）

2. Agent 生成唯一考试二维码并与考生信息绑定

3. Agent 支持试卷预览、人工审核确认后可发布；人事专员也可一键授权 Agent 直接发布

**输出：**
- 个性化试卷
- 考试二维码
- 考生-试卷对照台账

#### 3.1.4 面试自动阅卷与成绩输出

**功能描述：** Agent 在候选人完成答卷后自动完成全部科目的阅卷评分。

**输入：**
- 考生通过扫码登录进入考试界面
- 考生的全部作答记录

**处理规则：**

1. 客观题（单选、多选、判断）—— Agent 按标准答案自动实时批阅
   - 单选题：答对得满分，答错 0 分
   - 多选题：全部正确得满分；部分正确（选中了部分正确选项但未选任何错误选项）得 50% 分值；只要勾选任一错误选项得 0 分；未作答 0 分
   - 判断题：答对得满分，答错 0 分

2. 主观题（简答、论述、案例分析）—— 由 Agent 进行 AI 交叉评分（使用系统配置的两种不同 LLM 模型独立评分），若两者分值偏差≤10 分则取平均值；若偏差>10 分则标记为需人工复核。交叉评分模型从 7.3.1 节的模型管理配置中动态读取，具体模型版本以当次运行时生效的配置为准，不得在业务规则中硬编码模型名称，以确保系统支持模型平滑升级和灰度 A/B 测试。

3. Agent 自动汇总各科成绩，生成成绩单推送给人力资源端

**输出：**
- 考生个人成绩单及各题得分明细
- AI 主观题交叉评分报告（含两名模型的独立评分和差异说明）

#### 3.1.5 企业人才简历库

**功能描述：** 自动管理简历生命周期，从入库、标签化到到期处置。

**输入：** 经筛选后入库的简历

**处理规则：**

1. Agent 自动提取简历关键字段并建立索引
2. Agent 自动标注多维人才画像标签：行业背景、技术栈、管理经验、项目经验等
3. Agent 周期性执行简历健康检查，对入库后超过 180 天未更新的简历标记为"待刷新"并建议重新联系候选人
4. 超过保存期限的简历自动转入冷备存储（保留 3 年后按合规策略清理）
5. 支持以自然语言查询："找出所有有 5 年以上 Java 经验且做过微服务架构设计的候选人"

**输出：**
- 简历库（可按多维标签检索）
- 人才画像卡片

### 3.3 试用期管理

### 3.4 离职管理

#### 3.5.3 教材转视频 Agent（文档→视频）

**功能描述：** Agent 将 Word/PPT/PDF 形式的培训教材转换为短视频课程。

**输入：** 培训教材（Word、PPT 或 PDF）

**处理规则：**

1. Agent 读取教材并解析出关键知识点大纲
2. Agent 为每页内容匹配合适的图像素材或动画（"适合"的判定标准：图像素材与知识点内容相关度≥80%、分辨率≥720P、无版权纠纷；动画与讲解内容匹配度≥80%）。相关度和匹配度的计算方法：使用系统配置的 Embedding 模型（参见 7.3.1 节）将教材知识点文本与素材描述文本分别向量化，计算两者向量余弦相似度作为相关度/匹配度得分，得分 = 余弦相似度 × 100，取整数。基准为系统内置的知识-素材检索向量库，入库素材须经版权审核通过。
3. Agent 自动合成讲解旁白（支持 AI 配音）
4. Agent 生成标准化视频课程，存储至视频知识库
5. 人事专员可随时审核/修改/下架已生成的培训视频

**输出：**
- 培训视频（MP4 格式）
- 视频元数据（课时长度、知识点索引、适用岗位等）

### 3.7 考勤管理

#### 3.7.1 考勤数据采集与管理

**功能描述：** Agent 自动汇聚来自多源的考勤数据。

**输入：** 打卡设备原始打卡数据、员工请假/加班/出差申请记录

**处理规则：**

1. Agent 按既定周期自动从打卡设备/系统拉取打卡数据（支持指纹、人脸、IC 卡、APP 等多类终端）
2. Agent 接入请假、加班、出差审批数据作为出勤校正因素
3. Agent 自动将原始打卡时间与班次时间对照
4. Agent 标记以下异常（量化标准：当日零打卡记录、上下班打卡时间偏差超过班次允许范围±30分钟以上、同一分钟内重复打卡次数≥2次、连续 3 个工作日无打卡记录），此类异常统一标记为"待核实"状态

3. 自动标记以下异常类型：迟到、早退、缺卡、旷工、加班超限（超法定上限 36 小时/月，依据《国务院关于职工工作时间的规定》第 6 条及《劳动法》第 41 条规定：每月加班不得超过 36 小时）
4. Agent 生成完整的考勤异常清单推送到人事管理端
5. 如发现连续异常规律，Agent 自动提示可能的根源（如某班次长期存在打卡偏移现象）

- 个人考勤汇总表
- 部门考勤异常汇总
- 异常趋势分析报告

### 3.8 薪资管理

#### 3.8.1 薪资结构与规则管理

**功能描述：** Agent 维护薪资相关的基础规则和标准。

**处理规则：**

1. Agent 维护每位员工的薪资档案（基本工资、岗位津贴、交通补贴、通讯补贴、餐饮补贴、夜班补贴、绩效奖金基数等）
2. Agent 自动跟踪和收录国家最新社保缴费比例标准和最低工资标准调整
3. Agent 维护个税专项附加扣除数据的员工信息采集和更新机制
4. 薪资规则（加班系数、迟到扣款标准、补贴定额）由 Agent 统一管理，支持版本控制和生效时间

**输出：**
- 员工薪资主数据表
- 现行薪资规则库（带版本号）

#### 3.8.2 全自动薪资核算

**功能描述：** Agent 在每月指定日期自动启动并完成全员薪资核算。

**输入：** 本月考勤数据、员工薪资主数据、社保/公积金缴纳数据

**处理规则：**

1. Agent 从各子系统自动拉取当期核算所需的全部前置数据
2. Agent 按以下算式逐一运算：
   - 应发工资 = 基本工资 + 加班费 - 考勤扣款 + 交通补贴 + 通讯补贴 + 餐饮补贴 + 夜班补贴
   - 加班费 = 平日加班 1.5 倍时薪 + 周末加班 2 倍时薪 + 法定节假日加班 3 倍时薪（时薪 = 基本工资 ÷ 21.75 ÷ 8）
   - 加班超限标记：月累计加班时间超过 36 小时/月的部分自动标红并通知人事确认（与 3.7.2 节法定上限 36 小时/月保持一致，依据《国务院关于职工工作时间的规定》第 6 条及《劳动法》第 41 条）
   - 个人应缴社保 = 社保个人缴纳额
   - 个人应缴公积金 = 公积金个人缴纳额
   - 应税收入 = 应发工资 - 社保 - 公积金 - 免征额(5000 元) - 专项附加扣除
   - 个税按以下七级累进税率表计算（按月换算后的综合所得税率表）：

| 级数 | 月应纳税所得额区间（元） | 税率 | 速算扣除数 |
|------|------------------------|------|-----------|
| 1 | 不超过 3,000 | 3% | 0 |
| 2 | 超过 3,000 至 12,000 | 10% | 210 |
| 3 | 超过 12,000 至 25,000 | 20% | 1,410 |
| 4 | 超过 25,000 至 35,000 | 25% | 2,660 |
| 5 | 超过 35,000 至 55,000 | 30% | 4,410 |
| 6 | 超过 55,000 至 80,000 | 35% | 7,160 |
| 7 | 超过 80,000 | 45% | 15,160 |

   计算公式：个税 = 月应纳税所得额 × 适用税率 - 速算扣除数
   - 实发工资 = 应发工资 - 社保个人 - 公积金个人 - 个税

3. Agent 执行异常检测并标出不正常数值：
   - 实发额较上月波动超过 ±20%
   - 个税出现负数
   - 社保/公积金金额为 0 但状态为在职
   - 实发额低于当地最低薪资底线
   - 加班费突增幅度超过正常均值 2 个标准差（"正常均值"定义：以该员工近 6 个月的加班费算术平均值和标准差为统计基准）

4. Agent 将完整核算结果整理为标准格式推送给人事专员审核

5. **人事专员仅做审核动作**：查看 Agent 产出的核算报告，确认无误后点批确认

**输出：**
- 全员月度薪资明细表
- 薪资核算底稿（含每条数据的计算溯源）
- 异常数据清单

- 处理敏感个人信息前
- 与第三方共享个人信息前
- 系统重大升级可能影响个人信息权益时

**评估流程：**
1. 识别个人信息处理活动的范围和涉及的数据类型
2. 评估处理的合法性、正当性和必要性
3. 评估对个人信息权益的影响和安全风险等级
4. 制定风险缓解措施和安全保障方案
5. 形成 PIA 评估报告并存档（保存 ≥ 3 年）
6. 高风险评估结果须经系统管理员和人事主管双重审批通过后方可实施

| 网站改版适应性 | 面对目标网站改版/升级/页面结构变化，RPA 流程应具备自适应能力：定期（每周）验证 RPA 流程可用性，页面元素变化自动告警，失败率>5% 时触发流程重新配置 |

#### 5.1.4 短信 & 邮件通知服务

| 属性 | 详述 |
|------|------|
| 用途 | 提醒、验证码、通知推送 |

### 5.2 内部通信接口

#### 5.2.1 Agent 间消息传递

- Agent 间通过事件总线或消息队列（RabbitMQ/Kafka）交换数据与指令
- 消息格式统一为 JSON Schema 定义的结构化消息
- 每条 Agent 消息携带消息 ID、优先级、预期处理时间及 TTL

#### 5.2.2 Agent 编排调度器

- 统一的消息路由与状态机，维持每条端到端流程的事务性
- 支持流程的中途手动接管和重新分配
- 支持断点续跑（Agent 异常退出时可在断点处重新接续）

### 5.3 存储接口

#### 5.3.1 关系型数据库 (MySQL/PostgreSQL)

结构化数据持久化：用户信息、组织架构、薪资主数据、规则库、审计日志等。

#### 5.3.2 对象存储 (MinIO/OSS)

二进制文件存储：简历文件、证件扫描影像、签署协议、培训视频、截图回执等。

#### 5.3.3 缓存层 (Redis)

会话状态、排行榜、Agent 锁机制、短时热点数据。

#### 5.3.4 向量数据库（可选）

用于简历文本向量化检索、智能问答 Agent 的知识嵌入向量。

### 7.2 Agent 编排架构

Agent 编排层是本系统的"大脑"，负责将业务流程拆解为子任务并在正确的时机分配给合适的 Agent 执行。

#### 7.2.1 编排模式

1. **Pipeline 流水线** —— 适用于顺序执行的端到端流程（如：入职办理流程）。上游 Agent 产出下游 Agent 输入。
2. **Fan-Out/Fan-In 扇出扇入** —— 适用于需要并行处理的场景（如：薪资核算需要并行从考勤 Agent、补贴规则库、社保数据库获取数据）。
3. **Decision Tree 决策树** —— Agent 根据判断结果走向不同分支（如：简历筛选根据评分落入哪个区间执行不同的分拣动作）。
4. **Feedback Loop 反馈环** —— Agent 将执行结果反馈回编排层，编排层据此决定是否进入下一阶段或触发纠偏动作。

#### 7.2.2 状态持久化

- 每个业务流程拥有一个唯一 ID（UUID）。
- 流程进入任何一步后，其全部上下文和中间产出物持久化写入流程状态仓库，以确保任何时刻 Agent 崩溃都可以在断点恢复。

#### 7.2.3 Agent 间的契约与通信

- 采用消息队列(RabbitMQ/Kafka)解耦 Agent 之间的调用关系。
- 消息结构体通过 JSON Schema 严格定义，包括业务 ID、Agent 标识、优先级、超时、TTL。
- 每个消息都携带 trace-id 以支持全链路可追踪。

### 7.3 模型治理

#### 7.3.1 模型管理

| 模型类型 | 用途 | 选型方向 |
|---------|------|---------|
| LLM（大语言模型） | 简历语义理解、JD 匹配推理、文字生成（证明/报告）、聊天问询 | GPT-4/Claude/Qwen 等 |
| OCR 引擎 | 身份证、驾驶证、学历证书等证件信息识别 | PaddleOCR / 云服务 API |
| 人脸识别引擎 | 人脸采样、比对、活体检测 | Face++ / 本地部署方案 |
| Embedding 模型 | 简历文本向量化以支持相似性搜索 | text-embedding-3 / bge-m3 |
| ASR 模型 | 音频转写（如员工语音留言等场景） | Whisper 本地化模型 |

系统通过模型配置中心统一管理各 Agent 所使用的模型实例，业务规则中不得硬编码具体模型名称，模型切换和升级通过配置中心动态完成，确保模型可平滑升级。

#### 7.3.2 模型版本与 A/B 测试

- 每次模型更新以版本号发布，旧版本保留至少 30 天以便回滚
- 支持灰度 A/B 测试：新模型先用 5% 流量试运行，指标达标后再全量
- 每个 Agent 的评分输出都记录使用了哪一版本模型，以便追踪模型退化

#### 7.3.3 模型效能监控

- 对每个 Agent 的输出质量定期抽样复核
- 关键 Agent（评分 Agent、核算 Agent）的准确率指标纳入 Dashboard
- 系统维护基线值（初始值 ≥ 90%，按季度根据最新人工复核结果更新），当某 Agent 的准确率达到低于基线值 × 95% 时触发模型回归训练请求（例如基线为 90% 时，触发阈值为 90% × 95% = 85.5%）

### 7.4 错误恢复与自愈

1. Agent 在执行操作中发生异常时自动进入**重试队列**，按指数退避策略重试最多 3 次，初始延迟时间为 2 秒，退避系数为 2 倍（即第 1 次重试延迟 2 秒，第 2 次重试延迟 4 秒，第 3 次重试延迟 8 秒）
2. 重试仍然失败时将流程挂起到"待人工处理"状态，并向相关人员发送告警
3. Agent 在发起重试前自动生成故障摘要（Error Report）以便人工高效介入
4. 关键业务流程支持**手动中断接管**——当人类发现 Agent 行为异常时可以随时暂停并将控制权移交给自己

### 7.5 Agent 安全护栏(Guardrails)

| 护栏类型 | 说明 |
|---------|------|
| 金额操作护栏 | Agent 不得在未获人事专员审核批准的情况下修改任何金额的变动记录 |
| 对外通讯护栏 | Agent 发送邮件给外部联系人前需预审确认 |
| 数据删除护栏 | Agent 不得无条件删除已归档数据；只能移动归档位，删除动作需二次审批 |
| 模型推理护栏 | Agent 输出结果需经过合理性阈值检查（如薪资不得为零、评分不得超出 [0,100] 范围） |
| Prompt 注入防护 | 对用户输入和 Agent 内部 Prompt 统一注入安全过滤，防范越狱攻击 |

### 8.3 回退与降级方案

| 失效场景 | 降级策略 |
|---------|---------|
| LLM 不可用 | 简历筛选退化为关键词正则匹配模式（正则规则：JD 中的技能关键词和学历关键词与简历文本进行不区分大小写的正则匹配，匹配得分 = (命中关键词数 ÷ JD 关键词总数) × 100；退化验收标准：退化模式下 100 份测试简历的筛选结果与 LLM 可用时的一致性 ≥ 70%，且处理耗时 ≤ 500ms/份）；文书生成退化为预置模板填充（模板清单见 3.10 节） |
| OCR 服务不可用 | 证件信息改为人工录入；其余 Agent 不受影响 |
| 人脸比对服务宕机 | 降级到"身份证 + 手机验证码"模式完成身份校验 |
| Agent 编排层异常 | 退回各 Agent 手动调度模式：人事管理员在控制台手动触发单个 Agent |
| RPA 自动化被目标站拦截 | 转人工窗口操作；Agent 准备好预填数据减轻人工负担 |
| 数据库故障 | 自动切至从库(预计 15 分钟内切换)；若双主都宕机则进入只读模式维持前台查询 |

## 11. 上线切换与培训计划

### 11.1 上线切换策略

采取分阶段渐进上线，以降低业务冲击风险：

| 阶段 | 上线模块 | 过渡期 | 范围 |
|------|---------|-------|------|
| Phase 1 | 简历筛选 Agent、面试组卷、自动阅卷、入职 Agent | 2 周试点 | 选择一个部门试运行 |
| Phase 2 | 考勤 Agent、薪资 Agent、工资条、绩效 Agent | 全员推广 | 全部员工 |

| Phase 4 | 外务 Agent(RPA)、离职 Agent、证明 Agent | 正式切换 | 旧系统下线 |

### 11.2 切换窗口

- 最终切换安排在非工作日（周六/周日）
- 预计窗口：4-8 小时
- 切换前完成最终数据搬运
- 切换后执行完整性对账及业务贯通性检查

### 11.3 回退计划

- 切换后 48 小时内为安全观察期，期间如发生重大故障则在 30 分钟内回退到旧系统
- 回退前提：保留旧系统可访问，不做数据割裂

### 附录 C：Agent 运营规范

#### C.1 Agent 值班制度

- Agent 运营专员每日上班首件事件查看 Agent 运行 Dashboard，重点关注夜间运行的 Agent 是否有异常挂起任务
- 每周进行一次 Agent 运行健康回顾
- 每月向管理层提交一份 Agent 运行月报（自动化率、异常事件数、节省工时统计）

#### C.2 Agent 升级机制

- Agent 逻辑变更必须走 Code Review
- 上线新 Agent 前必须进行为期一周的 Shadow Run（后台并行运行但不对外输出结果，与原有操作对照比较产出一致性）
- 上线后经两周观察稳定后方可开启对外输出

#### C.3 成本监控

- 跟踪每月的 LLM API Token 用量和费用支出
- 设置用量预算告警阈（如月费用超过 5 万元发出黄色预警、超过 8 万元发出红色警报并要求暂停新增 Agent 调用）
- 对于频繁调用的高频低复杂度操作评估是否可以用规则引擎替代 LLM 推理，以降低成本
- **成本分摊：** 按部门/业务线分摊 AI 推理成本，每月生成各部门 AI 费用报表
- **ROI 分析：** 统计 Agent 自动化节省的工时成本与 AI 推理成本之比，目标 ROI ≥ 3:1（即每 1 元 AI 成本产生 ≥ 3 元人力节省）

#### D.3 错误处理统一规范

1. 所有 Agent 在执行过程中捕获异常时，必须按上述错误码体系记录错误码
2. 错误码记录写入 agent_run_log 表的 error_detail 字段，格式为：`{error_code}:{error_message}:{timestamp}`
3. 低级别错误（参数错误、数据不存在）由 Agent 自动处理并返回用户友好的提示信息
4. 中级别错误（外部服务超时、模型调用失败）按 7.4 节重试策略执行，重试失败后挂起
5. 高级别错误（系统内部异常、权限错误、数据完整性破坏）立即告警系统管理员，流程挂起
6. 所有错误码和用户友好提示文本映射表由系统管理员在配置中心统一管理，支持多语言
