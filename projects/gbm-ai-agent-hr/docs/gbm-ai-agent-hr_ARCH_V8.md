## 1. 架构概述

### 1.1 架构愿景

GBM AI Agent HR 是一套彻底 AI 原生的企业人力资源管理系统。系统核心设计理念为"零操作性"——所有可操作性事务均由 AI Agent 自主执行，人类用户仅承担战略性审核、争议仲裁和政策制定职责。

### 1.2 架构原则

1. **Agent-First**：每项功能以 AI Agent 为核心设计，不存在先人工后自动化的过渡路径
2. **松耦合的微服务架构**：各服务通过清晰的服务边界隔离，独立部署、独立升级
3. **事件驱动**：Agent 间通过消息队列异步通信，解耦调用关系
4. **配置驱动**：薪资规则、考勤规则、筛选权重等以配置化管理，Agent 读取参数自动计算
5. **端到端可追溯**：每条业务流程拥有唯一 ID，全链路 trace-id 追踪
6. **安全护栏**：关键操作设有自动阻断规则，需满足预设条件方可放行

## 2. 分层架构设计

### 2.1 展示层 (Presentation Layer)

**职责**：面向不同用户角色提供交互界面，统一入口。

**子层**：
- **Web UI**：面向人事专员、部门主管、系统管理员的桌面端操作界面
- **Mobile UI**：面向在职员工、新员工的移动端自助服务
- **扫码页**：PWA 应用，用于考试签到、培训签到等场景
- **通知渠道**：邮件和短信通知，由后端服务主动推送

**技术选型**：
- 框架：React 18 + TypeScript
- UI 库：Ant Design 5.x
- 移动端：React + PWA (Service Worker + Manifest)
- 构建工具：Vite
- 状态管理：Zustand（轻量级，适合 Agent 状态流）
- 路由：React Router v6
- HTTP 客户端：Axios + 请求拦截器

**关键设计决策**：
- 扫码页采用 PWA 方案，无需下载安装，微信扫码即可打开
- 所有页面支持 WCAG 2.1 AA 级无障碍标准
- 支持中/英双语切换，i18next 管理翻译资源

### 2.2 网关层 (Gateway Layer)

**职责**：统一入口，处理路由、认证、限流、日志。

**技术选型**：
- 反向代理：Nginx
- API 网关：Spring Cloud Gateway
- 认证中间件：JWT 令牌验证 + MFA 二因子校验

**网关功能清单**：
- 请求路由与负载均衡
- JWT 认证过滤（拦截非法请求）
- 速率限制（Redis 计数器实现）
- CORS 跨域处理
- 请求/响应日志记录
- 敏感操作 MFA 校验拦截
- 统一错误码映射

### 2.2.1 微服务通信治理

| 治理能力 | 技术方案 | 说明 |
|---------|---------|------|
| 服务发现 | K8s Native Service Discovery | K8s DNS 解析服务名（Nacos 仅作为配置中心，非注册中心） |
| mTLS | K8s NetworkPolicy + Vault TLS 证书 | K8s NetworkPolicy 限制 Pod 间通信，敏感服务间通过 Vault 管理的 TLS 证书实现双向认证（mTLS），避免引入完整服务网格控制平面 |
| 熔断限流 | Resilience4j | 滑动窗口 100 个样本，失败率 >50% 触发熔断，30s 后半开探测 |
| 负载均衡 | Spring Cloud LoadBalancer | Round-Robin 策略 |
| 链路追踪 | OpenTelemetry | 自动注入 trace-id 到 HTTP 头和 RabbitMQ 消息头 |

> **方案选择说明**：当前规模（11 业务服务 + 20 Agent 实例）采用轻量方案（Resilience4j + K8s Service），不引入完整服务网格（Istio Sidecar 模式），预计可减少 30% 的内存开销和 200ms 的延迟。待服务数量 >50 后评估升级为完整服务网格。

### 2.3 业务服务层 (Service Layer)

**职责**：承载各业务模块的后端 API 服务，负责 HTTP 接口暴露、数据持久化、事务管理和安全控制。业务服务是 Agent 所需数据的提供者，而非 Agent 的运行时环境——Agent 作为独立的容器化进程运行，通过 RPC/HTTP 调用业务服务接口获取数据、通过消息总线与业务服务进行事件驱动交互。

**架构模式**：松耦合的微服务架构

**选择理由**：
- 各服务通过清晰的服务边界隔离，独立部署、独立升级
- 基于 DDD 领域划分微服务，降低服务间耦合度
- 每个服务拥有独立的数据库 Schema，避免共享数据库
- 满足 SRS7.4 故障自愈和独立扩缩容要求

> **SRS7.4 故障自愈和独立扩缩容要求**：每个微服务和 Agent 必须具备健康检查接口，支持 K8s liveness/readiness probe；故障时自动重启或替换 Pod；支持基于 CPU/内存/请求量的自动扩缩容（HPA），扩缩容不影响其他服务。

**服务清单**：

| 服务 | 包路径 | 职责 |
|------|--------|------|
| auth | `com.gbm.hr.auth` | 认证授权、RBAC、MFA |
| recruitment | `com.gbm.hr.recruitment` | 招聘管理、简历筛选、面试管理 |
| onboarding | `com.gbm.hr.onboarding` | 入职办理、证件识别、人脸建档 |
| training | `com.gbm.hr.training` | 培训管理、签到、考试、证书 |
| attendance | `com.gbm.hr.attendance` | 考勤采集、异常识别 |
| payroll | `com.gbm.hr.payroll` | 薪资核算、工资条发放 |
| performance | `com.gbm.hr.performance` | 绩效管理、考核汇总 |
| external | `com.gbm.hr.external` | 外务管理（工伤、公积金 RPA） |
| employee | `com.gbm.hr.employee` | 员工档案、离职管理、证明开具 |
| notification | `com.gbm.hr.notification` | 邮件、短信、推送通知 |
| audit | `com.gbm.hr.audit` | 审计日志、操作追踪 |

### 2.4 Agent 编排层 (Orchestration Layer)

**职责**：业务流程编排、Agent 调度、状态持久化、断点恢复。

**技术选型**：
- 流程引擎：Camunda 8 (Zeebe) — 原生支持事件驱动和高并发
- 消息队列：RabbitMQ — 与微服务架构更匹配、运维复杂度更低
- 自定义编排 SDK：Java 实现的 Agent 内部推理-行动循环客户端（Agent SDK）；RPA Agent 使用 Python SDK（Playwright 生态）

**Camunda 8 与自定义 SDK 的边界**：
- Camunda 8 (Zeebe) 负责**业务流程编排**：定义跨 Agent 的 BPMN 流程（如入职流程、薪资核算流程），管理流程实例状态、节点流转、断点恢复；原生支持事件驱动架构和高并发场景
- 自定义 Agent SDK 负责**Agent 内部的推理-行动循环**：每个 Agent 接收 Camunda 触发的任务后，SDK 管理感知→推理→行动的迭代过程，包括 LLM 调用、工具使用、结果校验
- 两者协作方式：Camunda 8 流程定义中的 Service Task 节点通过 SDK 调用对应 Agent，Agent 完成后返回结果，Camunda 8 继续推进流程

**Camunda 8 与 RabbitMQ 集成方案**：

- Camunda 8 (Zeebe) 原生消息流基于 Kafka，本架构选择 RabbitMQ 作为统一事件总线以降低运维复杂度
- 集成方式：使用 Camunda 8 的 Message Correlation 机制配合自定义消息桥接层
- Zeebe 的 Message 通过 Java SDK 发布到 RabbitMQ Topic Exchange，RabbitMQ 消费者处理后通过 Zeebe publishMessage API 回调 Correlation Key 完成流程推进
- 桥接层设计：Camunda-Zeebe-Bridge 服务负责双向消息转换（Zeebe Message ↔ RabbitMQ AMQP Message）
- 消息一致性：采用 At-Least-Once 投递 + 幂等键去重

**桥接方案评估**：已评估直接使用 Zeebe 原生 Kafka 消息流和改用 Camunda7（原生支持 RabbitMQ）两种替代方案。选择桥接方案的原因：Zeebe Kafka 流需要额外运维 Kafka 集群，增加运维复杂度；Camunda7 为旧版引擎，不支持原生事件驱动和高并发。最终保留桥接方案，但桥接服务将设计为无状态、高可用部署（至少 2 个副本），降低单点故障风险。

**编排模式**：

| 模式 | 应用场景 | 示例 |
|------|---------|------|
| Pipeline 流水线 | 顺序执行端到端流程 | 入职办理流程 |
| Fan-Out/Fan-In | 并行处理后汇聚 | 薪资核算并行拉取数据 |
| Decision Tree | 条件分支 | 简历评分分拣 |
| Feedback Loop | 结果反馈决定是否继续 | 材料校验-补传循环 |

**状态持久化设计**：
- 每个业务流程分配唯一 UUID 作为 `flow_id`
- 流程进入任一步骤后，完整上下文和中间产物写入 `process_instance` 表
- Agent 崩溃后可根据 `flow_id` 从断点恢复执行

### 2.5 AI 模型服务层 (AI Model Layer)

**职责**：提供 AI 推理能力，屏蔽模型细节，统一接口。

**服务清单**：

| 服务 | 技术选型 | 部署方式 |
|------|---------|---------|
| LLM 推理 | vLLM + Qwen/DeepSeek 等 | 本地 GPU 服务器或云端 API |
| OCR 识别 | PaddleOCR | 本地部署 |
| 人脸识别 | 本地部署 (FaceNet/OpenFace) | 本地部署（数据不出境、隐私优先） |
| Embedding | bge-m3 或 text-embedding-3 | 本地 CPU 可运行 |
| ASR 语音 | Whisper (本地化) | 本地部署 |
| 多模态 | Qwen-VL 或 GPT-4V API | 云端 API |

**模型治理**：
- 每个模型服务封装为独立微服务
- 统一 gRPC/HTTP 接口，Agent 无需感知底层模型差异
- 模型版本管理：每次更新带版本号，旧版本保留 30 天
- A/B 测试：新模型 5% 流量灰度，指标达标后全量

### 2.6 数据基础设施层 (Data Infrastructure Layer)

| 组件 | 用途 | 规格 |
|------|------|------|
| MySQL 8.x | 结构化数据存储 | 主从复制，InnoDB 引擎 |

## 3. 模块划分与职责

### 3.1 招聘管理模块

**包含 Agent**：招聘渠道 Agent、简历匹配 Agent、组卷 Agent、阅卷 Agent

**核心流程**：
1. 岗位需求录入 → 招聘渠道 Agent 发布
2. 简历抓取 → 简历匹配 Agent 评分分拣
3. 面试安排 → 组卷 Agent 出题 → 阅卷 Agent 评分

**关键接口**：
- 简历批量导入 (Excel/CSV)
- 招聘平台 API 对接 (前程无忧、中国人才热线)
- 题库管理 CRUD
- 试卷生成与发布
- 成绩导出

### 3.2 入职管理模块

**包含 Agent**：入职引导 Agent、OCR Agent、人脸 Agent

**核心流程**：
1. 新员工扫码 → 入职引导 Agent 引导材料上传
2. OCR Agent 识别证件 → 结构化信息提取
3. 人脸 Agent 采集 → 比对建档

**关键接口**：
- 扫码登录 (JWT 临时令牌)
- 文件上传 (MinIO)
- OCR 识别调用
- 人脸采集与比对
- 电子协议签署

### 3.3 培训管理模块

**包含 Agent**：培训 Agent、教材转视频 Agent、审核资料 Agent

**核心流程**：
1. 培训计划自动生成 → 签到二维码生成
2. 扫码签到 → 自动统计
3. 结业考试 → 自动阅卷 → 证书生成
4. 教材转视频 Agent 将文档转为教学视频

**关键接口**：
- 培训计划 CRUD
- 签到记录
- 考试管理
- 视频生成与存储
- 资料包打包与导出

### 3.4 考勤管理模块

**包含 Agent**：考勤 Agent

**核心流程**：
1. 定时拉取打卡数据
2. 与排班表对照
3. 异常识别与标记
4. 汇总报表生成

**关键接口**：
- 打卡设备数据接入 (多厂商适配器)
- 请假/加班/出差审批数据接入
- 考勤异常告警
- 考勤报表导出

### 3.5 薪资管理模块

**包含 Agent**：薪资 Agent、工资条 Agent

**核心流程**：
1. 月末定时触发薪资核算
2. **数据快照**：核算触发时对各数据源（考勤、补贴、社保、公积金）做时间戳快照，生成 `payroll_snapshot_{year_month}_{snapshot_id}`，确保所有数据对应同一结算周期
3. 基于快照并行拉取数据，不直接读取实时数据
4. 执行核算公式计算
5. 异常检测与标记
6. 推送人事专员审核
7. 审核后工资条 Agent 批量发放

**数据一致性保障**：
- 快照机制：每次薪资核算生成唯一 `snapshot_id`，关联该周期所有数据源的时间戳
- 快照存储：快照数据写入 `payroll_snapshot` 表，保留最近 12 个月
- 可追溯性：每条薪资记录携带 `snapshot_id`，可回溯到核算时的原始数据

**关键接口**：
- 薪资规则配置 (版本管理)
- 薪资主数据管理
- 社保/公积金缴费数据接入
- 个税计算 (七级累进税率)
- 工资条发送 (短信/邮件/APP)

### 3.6 绩效管理模块

**包含 Agent**：绩效 Agent

**核心流程**：
1. 考核期初提醒各部门确定方案
2. 发送自评链接 → 回收汇总
3. 推送上级审批
4. 汇总分析与报表生成

### 3.7 外务管理模块

**包含 Agent**：外务 Agent、RPA Agent

**核心流程**：
1. 工伤/公积金事件触发
2. RPA Agent 登录政府网站
3. 自动填表、提交、截图回执
4. 跟踪进度与通知

**关键技术**：
- Playwright 无头浏览器集群
- 凭证加密管理 (Vault)
- 网站改版自适应检测 (每周验证)

**RPA 容错与降级方案**：
- **重试策略**：单页操作失败时指数退避重试（1s→5s→15s），最多 3 次；整流程失败时 30 分钟后重试，最多 2 次
- **降级方案**：当 RPA 连续失败 ≥3 次或网站改版检测失败时，自动触发告警（邮件+短信通知 HR 专员），转为人工处理模式
- **人工介入 SLA**：告警发出后 2 小时内 HR 专员需确认并手动完成申报，超时自动升级通知部门负责人
- **截图审计**：每次 RPA 操作自动截取关键页面（登录页、填表页、提交回执页），存储至 MinIO 作为操作凭证
- **选择器版本管理**：每个目标网站维护 DOM 选择器版本库，网站改版时自动比对并标记失效选择器

**RPA 安全护栏**：
- **容器网络隔离**：RPA 容器运行在独立的 K8s NetworkPolicy 中，仅允许访问政府网站域名白名单（如 `*.gov.cn`、`*.gov.tw`），禁止访问内网其他服务
- **沙箱机制**：Playwright 容器以只读根文件系统运行，临时文件写入 tmpfs（容器销毁后自动清除），禁用 Docker socket 挂载，禁止特权模式
- **外网访问控制**：通过 Squid 代理转发所有外网请求，记录完整请求/响应日志，支持按域名/IP/URL 模式拦截
- **资源限制**：每个 RPA 容器限制 CPU ≤ 2 核、内存 ≤ 4GB，防止浏览器进程资源耗尽影响宿主节点

### 3.8 综合服务模块

**包含 Agent**：证明 Agent、预算 Agent、分析 Agent、离职 Agent

**职责**：
- 证明 Agent：各类人事证明自助签发
- 预算 Agent：费用单据 OCR、分类、汇总
- 分析 Agent：跨模块数据分析洞察
- 离职 Agent：离职交接、证明开具、资料归档

### 3.9 跨服务事务一致性

微服务架构下，跨服务操作（如入职流程涉及 onboarding 服务、auth 服务、employee 服务）采用 **Saga 模式** 保证数据一致性：

- **编排式 Saga**：由 Camunda 8 流程引擎作为协调器，编排各步骤的执行顺序和补偿逻辑
- **补偿机制**：每个业务步骤定义对应的补偿操作（如"创建员工记录"的补偿为"撤销入职申请"），当某步骤失败时自动触发前置步骤的补偿
- **事件驱动**：每个步骤完成后发布事件触发下一步，失败时发布补偿事件
- **幂等性保证**：所有服务接口支持幂等键（idempotency-key），防止重复执行

**典型场景 - 入职流程**：

| 步骤 | 服务 | 操作 | 补偿操作 |
|------|------|------|---------|
| 1 | onboarding | 创建入职申请 | 撤销申请 |
| 2 | auth | 创建系统账号 | 删除账号 |
| 3 | employee | 创建员工档案 | 标记档案无效 |
| 4 | onboarding | 发送入职通知 | 撤销通知 |

**补偿失败处理策略**：
- 补偿操作本身失败时，记录失败原因至 process_instance 表的 error_detail 字段
- 自动重试：补偿操作支持最多 3 次重试（指数退避 1s→5s→15s）
- 死信队列：重试耗尽后，补偿失败事件写入死信队列（RabbitMQ DLX 机制），同时触发紧急告警（电话+短信，5 分钟内通知）
- 人工介入流程：运维人员收到告警后，登录管理控制台查看补偿失败详情，手动执行补偿操作或标记为'可忽略'
- 补偿审计：所有补偿操作（包括成功、失败、人工介入）写入 audit_log 表，操作类型标记为 COMPENSATION

### 4.5 数据库版本管理

采用 **Flyway** 进行数据库 Schema 的版本控制：

- **迁移脚本管理**：所有表结构变更以 SQL 脚本形式存放于 `db/migration/` 目录，命名规则为 `V{version}__{description}.sql`（如 `V1.2.0__add_employee_table.sql`）
- **自动化执行**：应用启动时自动检查 `flyway_schema_history` 表，执行未应用的迁移脚本
- **版本回滚**：支持编写反向迁移脚本（如 `R1.2.0__rollback_employee_table.sql`），用于测试环境回滚
- **环境隔离**：开发/测试/生产环境使用独立的 Flyway 配置，禁止跨环境执行迁移
- **变更审批**：生产环境 Schema 变更需经过代码审查 + 测试验证 + DBA 审批流程

## 5. Agent 群架构

### 5.1 Agent 运行时

Agent 作为**独立容器化进程**运行，部署在与业务服务分离的专属 Agent Pod 中，每个 Agent 拥有独立的容器、独立的扩缩容策略和故障自愈能力（满足本文档 2.3 节定义的需求（原 SRS7.4）要求）。按业务域划分以下 Agent 服务，每个服务独立部署和独立升级：
- **招聘 Agent 服务**：合并渠道+简历+组卷+阅卷 4 个 Agent
- **入职 Agent 服务**：合并入职引导+OCR+人脸 3 个 Agent
- **培训 Agent 服务**：合并培训+教材转视频+审核资料 3 个 Agent
- **考勤 Agent 服务**：考勤 Agent 独立运行
- **薪资 Agent 服务**：合并薪资+工资条 2 个 Agent
- **绩效服务 Agent**：绩效管理、考核汇总
- **外务 RPA 服务 Agent**：外务管理+RPA 自动化（工伤、公积金）
- **离职服务 Agent**：离职交接、证明开具、资料归档
- **证明开具 Agent**：各类人事证明自助签发
- **预算管理 Agent**：费用单据 OCR、分类、汇总
- **数据分析 Agent**：跨模块数据分析洞察

Agent 服务以独立容器化进程部署，每个 Agent 拥有独立的进程空间。Agent 间通过 RabbitMQ 事件总线异步通信，Agent 与业务服务之间通过 HTTP/RPC 接口交互。**Agent 不嵌入业务服务内部运行，业务服务也不作为 Agent 的宿主进程**。

**部署粒度说明**：同一业务域的多个 Agent 合并为一个 Agent 服务，部署为独立的 K8s Pod（如招聘 Agent 服务包含渠道+简历+组卷+阅卷 4 个 Agent，共享同一个容器）。每个 Agent 服务拥有独立的扩缩容策略（HPA），以 Agent 服务为扩缩容粒度，而非单个 Agent。Agent 服务间通过 RabbitMQ 事件总线异步通信。

**Agent SDK 设计**：
- **SDK 职责**：每个 Agent 内置 Agent SDK，负责管理感知→推理→行动的迭代循环，包括 LLM 调用、工具使用、结果校验
- **生命周期管理**：Agent 启动时初始化 SDK → 从 Vault 加载凭证 → 订阅 RabbitMQ 队列 → 就绪（通过 K8s Service Discovery 自动提供服务发现，无需手动注册）；停止时有序释放资源 → 取消订阅 → K8s Pod 终止后服务自动下线
- **工具注册机制**：采用注解驱动方式，开发者通过 `@Tool` 注解标记方法，SDK 在初始化时自动扫描并注册至 Agent 的工具集，同时自动生成工具描述文档供 LLM 参考
- **LLM 调用超时策略**：单请求超时 30s，支持重试 2 次（指数退避 1s→3s），流式响应支持逐 token 回调，支持中断和撤销
- **异常处理**：SDK 内置推理链日志记录，LLM 调用失败时自动降级至规则引擎，Agent 崩溃后根据 flow_id 从断点恢复
- **技术栈说明**：业务 Agent 使用 Java SDK（与 Spring Boot 集成），RPA Agent 使用 Python SDK（Playwright 浏览器自动化），OCR Agent 使用 Python SDK（PaddleOCR）。各 SDK 通过统一的 HTTP/gRPC 接口与 AI 模型服务层通信。

Agent 运行时包含以下组件：


### 5.2 Agent 通信协议

Agent 间通信采用 **RabbitMQ 作为传输层 + JSON 作为消息格式** 的统一模式，不存在两套通信机制。RabbitMQ 负责消息路由、持久化、重试和负载均衡，JSON Schema 定义了所有 Agent 间消息的统一格式：

```json
{
  "message_id": "uuid",
  "trace_id": "uuid",
  "flow_id": "uuid",
  "source_agent": "agent_name",
  "target_agent": "agent_name",
  "priority": "HIGH|MEDIUM|LOW",
  "ttl_seconds": 3600,
  "payload": {
    "action": "string",
    "data": {}
  },
  "timestamp": "2026-06-12T10:00:00Z"
}
```

**通信模式**：
- **发布/订阅**：通过 RabbitMQ Topic Exchange 实现，用于广播型通知（如简历入库通知招聘+分析 Agent）
- **请求/响应**：通过 RabbitMQ 队列+Reply-To 实现，用于 Agent 间直接协作（如 OCR Agent 向人脸 Agent 请求比对）
- **事件溯源**：所有消息持久化至事件日志表，支持事后审计和流程重放

### 6.4 部署模式

| 模式 | 适用场景 | AI 推理位置 |
|------|---------|------------|
| 公有云 SaaS | 中小型企业 | 云端 GPU API |
| 私有云 | 大型企业、数据主权要求高 | 本地 GPU 服务器 |
| Hybrid | 敏感数据本地、推理云端 | 混合部署 |

### 6.5 高可用设计

- API 网关：至少 2 个 Pod，Ingress 负载均衡
- 业务服务：每个服务至少 2 个副本，支持独立自动扩容
- MySQL：主从复制，自动故障切换 (15 分钟内)
- Redis：Cluster 模式，3 主 3 从
- RabbitMQ：集群部署，支持镜像队列

### 6.6 灾备设计

- **RPO 目标**：≤ 5 分钟（基于 MySQL binlog 实时同步）
- **RTO 目标**：≤ 2 小时（应用层无状态，重启即可恢复）
- **异地灾备**：生产数据中心 + 异地灾备中心，MySQL 主从异步复制，RPO ≤ 5 分钟
- **数据备份策略**：
  - 全量备份：每周日凌晨 2:00 执行，保留≥15年（薪资数据、工伤档案、电子协议等）
  - 增量备份：每日凌晨 3:00 执行，保留≥1年
  - 备份存储：MinIO 对象存储 + 离线磁带库（每月归档）
  - 备份验证：每月随机恢复 1 个备份集进行校验
- **备份自动化工具**：
  - **数据库备份**：Percona XtraBackup（MySQL 热备），通过 XXL-JOB 调度 BackupJob 执行
  - **对象存储备份**：rclone 同步 MinIO 到异地 S3 兼容存储
  - **K8s 资源备份**：Velero 备份 PV/ConfigMap/Secret，每日执行
  - **备份验证**：每月自动恢复测试，结果写入监控看板
- **灾难恢复流程**：主数据中心不可用时，切换至异地灾备中心，DNS 切换 + 应用重新部署，预计 2 小时内恢复服务
- **数据生命周期管理**：
  - 遵循 PIPL 数据最小化原则，过期数据按数据分类执行差异化清理策略
  - 全量备份保留≥15年的数据（薪资数据、工伤档案、电子协议）为法律强制保留，不涉及个人隐私数据清理
  - 个人信息数据（身份证号、人脸特征、住址等）在员工离职后 3 年自动脱敏处理（保留统计用途的聚合数据，删除可识别个人身份的原始数据）
  - 考勤数据在线保留 24 个月，之后归档至冷备表，原始明细数据在归档后 5 年自动清理
  - 简历数据在候选人未被录用后 1 年自动脱敏（保留技能标签聚合数据用于招聘分析）
  - 数据清理操作需经 HR 管理员审批，清理记录写入 audit_log 表

## 7. 安全架构

### 7.1 认证与授权

- **认证方式**：JWT 令牌 + MFA 二因子认证
- **MFA 强制场景**：管理员首次登录、访问薪资数据、公积金/社保操作、大批量导出、密码重置
- **授权模型**：RBAC（基于角色的访问控制）
- **数据行级隔离**：部门主管仅可查看本部门下属数据
- **临时授权**：面试官凭二维码登录，时效 ≤ 2 小时

### 7.2 数据安全

- **加密存储**：AES-256 加密敏感字段（身份证号、人脸特征、薪资数据）
- **传输加密**：强制 TLS 1.2+
- **密钥管理**：HashiCorp Vault 管理加密密钥，定期轮换
- **数据不出境**：符合 PIPL 要求，数据存储在中国境内

### 7.3 操作审计

- **审计字段**：操作时间、操作人、IP、操作类型、模块、对象、前后快照、结果、耗时
- **不可篡改**：审计日志写入独立存储，保藏 ≥ 10 年
- **审计范围**：所有增删改查、导出、登录登出、Agent 调用操作

### 7.4 Agent 安全护栏

| 护栏类型 | 规则 |
|---------|------|
| 金额操作 | 未获审核批准不得修改金额变动记录 |
| 对外通讯 | 发送外部邮件前需预审确认 |
| 数据删除 | 不得无条件删除归档数据，删除需二次审批 |
| 推理校验 | 输出结果过合理性阈值检查（薪资非零、评分 [0,100]） |
| Prompt 注入 | 用户输入和内部 Prompt 统一安全过滤 |

## 9. 非功能性设计决策

### 9.1 性能设计

| 指标 | 目标值 | 计算依据 |
|------|--------|---------|
| 简历匹配单份 | < 2 秒 | Embedding 向量化 200ms + 向量检索 50ms + LLM 推理 800ms(缓存命中率 60%) + 规则评分 50ms = ~1.1s(P95) |
| 批量简历处理 100 份 | < 5 分钟 | 并行度 10，单份 2s × 10 批 = 200s ≈ 3.3 分钟（含 LLM 批量请求优化） |
| 全员薪资核算 500 人 | ≤ 2 分钟 | 数据快照 30s + 并行拉取 5 数据源(各 30s) + 核算计算 500 人×50ms=25s + 异常检测 10s = ~2 分钟 |
| 签到并发 ≥ 200 人 | P95 ≤ 5 秒 | Redis 缓存读写 < 5ms + 数据库写入 50ms + 人脸比对 200ms，总 P95 ≈ 500ms，200 并发下队列等待 < 4.5s |

**基准测试假设**：
- LLM 推理延迟：本地 vLLM 部署 Qwen-7B，单请求 P50=500ms，P95=1200ms；开启 KV Cache 后缓存命中率 60%（测试环境：NVIDIA A100 80GB，CUDA 12.1，vLLM 0.3.0，基准测试日期 2026-05-15，测试脚本见 `scripts/benchmarks/llm_latency.py`）
- 数据库 TPS：MySQL 主库预估 2000 TPS（4 核 8G，InnoDB 缓冲池 4G）
- 批量并行度：薪资核算 5 个数据源并行拉取，简历处理 10 路并行

### 9.2 可靠性设计

- **回退机制**：Agent 操作前生成状态快照，30 秒内可恢复
- **重试策略**：指数退避，最多 3 次重试
- **降级触发条件**：LLM 连续失败 >=3 次或单次超时 >60s 时触发降级
- **降级状态机**：NORMAL → DEGRADED（通知运维） → RECOVERED（健康检查通过3次自动恢复）
- **降级后的通知**：企业微信/邮件通知运维团队 + 前端 Dashboard 显示降级状态
- **具体降级策略**：简历筛选退化为 TF-IDF 关键词匹配 + 规则评分；OCR 不可用时转人工上传结构化表单；人脸比对不可用时暂停入职流程并告警
- **自动恢复**：每 5 分钟执行健康探测，连续 3 次成功后自动恢复至 NORMAL 状态
- **数据一致性**：薪资等核心操作提供可复核底稿

### 9.3 可扩展性设计

- 招聘平台扩展：新增渠道适配模块即可
- 打卡外设扩展：新增数据接入适配器
- AI 模型升级：更换底层 LLM/API 不影响上层业务逻辑
- Agent 数量扩展：独立容器化 Agent 支持水平扩展

### 9.4 可维护性设计

- 配置驱动：规则以 YAML/JSON 配置，Agent 读取计算
- 热更新：系统参数通过 Nacos 控制台在线热更
- 独立升级：各微服务和 Agent 可独立升级，不影响其他模块
- 完整日志：全链路操作日志便于追溯排查
