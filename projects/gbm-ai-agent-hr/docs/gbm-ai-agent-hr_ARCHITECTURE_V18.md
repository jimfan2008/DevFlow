## 1. 架构概述

### 1.1 设计目标

GBM AI Agent HR 系统采用 **AI 原生微服务架构**，以 AI Agent 为系统核心执行主体，实现人力资源管理全流程的自动化。架构设计遵循以下原则：

1. **零操作性原则** — 所有操作性事务由 Agent 自主完成，人类仅承担审核与仲裁
2. **适度微服务** — 按业务域合理聚合为 **4 个域服务**（V15 修订：从 V14 的 8 个服务群合并为 4 个），避免过度拆分导致的数据分散和跨服务调用爆炸。合并理由详见第 6.1 节
3. **事件驱动** — 域服务间通过消息队列异步通信
4. **配置驱动** — 业务规则（薪资、考勤、筛选权重）以配置形式管理
5. **可观测性** — 完整的链路追踪（OpenTelemetry + Jaeger，详见第 2.4.1 节）、日志、监控
6. **服务治理** — 通过 K8s Service + Resilience4j 应用层熔断统一管理服务间通信（详见第 6.6 节服务治理方案）

## 2. 分层架构设计

### 2.1 展示层 (Presentation Layer)

展示层负责用户交互界面和消息推送，包含以下组件：

| 组件 | 技术选型 | 职责 |
|------|----------|------|
| Web 应用 | Vue 3 + Element Plus | HR 审核面板、数据查看、报表展示 |
| 移动端 | UniApp | 移动端审核、通知接收、扫码入口 |
| 扫码入口 | H5 (Vue 3) | 面试签到、培训签到、访客登记 |
| 通知推送 | 短信网关 + 邮件服务 | 审核通知、提醒、状态变更通知 |

**设计说明：** 展示层仅提供"查看"和"审核"功能，不提供操作性功能。所有数据录入、资料整理、表单填写等操作均由 Agent 完成。

### 2.2 网关层 (Gateway Layer)

V15 修订：移除 Spring Cloud Gateway，采用 K8s Nginx Ingress Controller 作为统一入口。

```
                    互联网
                      |
              +-------+-------+
              |  K8s Ingress  |
              |  Controller   |
              +---------------+
              |               |
    +---------+         +-----+--------+
    | Nginx (L7) |       | Nginx (L7)  |
    +---------+         +-----+--------+
              |               |
    +---------+-------+ +-----+--------+
    |  static.resources |  /api/* routes |
    +-------------------+ +--------------+
```

**职责划分：**
- SSL 证书终止、路由转发、静态资源服务由 Nginx Ingress 处理
- 鉴权（JWT 验证）、限流、请求日志下沉至 Agent 服务内部处理
- 好处：减少一层服务跳转，降低延迟；Agent 服务自主管理安全策略

### 2.3 编排调度层 (Orchestration Layer)

```
+---------------------------------------------------------------+
|                    Camunda 8 / Zeebe                           |
|  +------------------+  +------------------+  +--------------+ |
|  | BPMN 流程定义    |  | 并行网关 (Parallel)|  | 排他网关     | |
|  | (招聘流程、入职   |  |  (证件识别并行     |  | (审核/驳回)  | |
|  |   流程、离职流程) |  |    人脸比对等)    |  |              | |
|  +------------------+  +------------------+  +--------------+ |
|  +---------------------------------------------------------+ |
|  |  Worker 池 — 每个域服务注册为 Zeebe Worker               | |
|  |  任务类型：简历筛选、证件识别、薪资计算、RPA 操作等        | |
|  +---------------------------------------------------------+ |
+---------------------------------------------------------------+
```

**核心组件：**

1. **流程定义引擎 (Camunda 8/Zeebe)**
   - 基于 BPMN 2.0 标准定义业务流程
   - 支持并行网关（如证件识别并行执行）、排他网关（审核通过/驳回）
   - 流程版本管理，支持灰度发布

2. **任务分解器 (Task Decomposer)**
   - 将复杂任务（如"入职办理"）分解为子任务
   - 子任务映射到对应的 Agent Worker
   - 支持任务优先级和依赖关系管理

3. **状态管理器 (State Manager)**
   - Redis 存储流程实例状态（TTL = 30 天）
   - MySQL 持久化流程历史（用于审计和追溯）
   - 支持断点恢复：Agent 失败后可从上一个检查点继续

### 2.4 域服务层 (Domain Services Layer)

4 个域服务是系统的核心业务执行层，每个域服务内部包含多个 Agent 模块。

#### 2.4.1 链路追踪设计

全系统采用 OpenTelemetry 进行分布式链路追踪：

```
User Request → Ingress → [TraceID] → Domain Service → [SpanID] →
  → Kafka Event → [TraceID] → Downstream Service → [SpanID]
```

| 组件 | 追踪方式 | 实现 |
|------|----------|------|
| HTTP 请求 | W3C Trace Context 头 | OpenTelemetry Java Agent |
| Kafka 消息 | 消息头注入 TraceContext | Kafka Tracing Interceptor |
| 数据库查询 | SQL 查询 Span | OpenTelemetry JDBC Instrumentation |
| Agent 任务 | 自定义 Span | Zeebe 原生 Trace ID 集成 |

**链路追踪数据存储：** Jaeger (All-in-one 模式，单节点部署)

### 2.5 共享基础设施层 (Shared Infrastructure)

| 服务 | 端口 | 职责 | 调用方 |
|------|------|------|--------|
| OCR 服务 | 8085/OCR | 身份证、学历证、银行卡识别 | 用户中心域、招聘培训域 |
| RPA 服务 | 8085/RPA | 社保局、公积金网站自动化操作 | 薪酬考勤域、用户中心域 |
| 文件处理 | 8085/File | 文档合并、PDF 生成、图片压缩 | 所有域服务 |

**设计说明：** auto-agent 作为共享基础设施服务，被多个域服务调用。这不是一个独立的业务 Agent，而是提供通用能力的工具服务。

### 2.6 AI 模型服务层 (AI Model Services)

| 模型服务 | 技术选型 | 部署方式 | 资源需求 |
|----------|----------|----------|----------|
| LLM 推理 | vLLM + Qwen-72B-AWQ | 本地 GPU 服务器 | 1× NVIDIA A100 (80GB) |
| OCR 推理 | PaddleOCR | 本地 CPU 服务器 | 4 Core, 8GB RAM |
| 人脸服务 | InsightFace (本地) | 本地 CPU 服务器 | 4 Core, 8GB RAM |
| Embedding | bge-m3 | 本地 CPU 服务器 | 2 Core, 4GB RAM |

**RPO/RTO 保障方案 (2.6.1)：**

| 模型服务 | RPO (数据丢失) | RTO (恢复时间) | 保障措施 |
|----------|----------------|----------------|----------|
| vLLM | 模型权重不丢失（只读） | < 30 分钟 | Docker 容器重启 + 模型缓存预热 |
| PaddleOCR | 不丢失（只读模型） | < 15 分钟 | 容器重启即恢复 |
| InsightFace | 不丢失（只读模型） | < 15 分钟 | 容器重启即恢复 |
| bge-m3 | 不丢失（只读模型） | < 10 分钟 | 容器重启即恢复 |

**Milvus 单节点 RPO/RTO 保障方案 (2.6.2)：**

由于向量数据（简历嵌入、文档嵌入等）属于可重建数据，Milvus 单节点采用以下备份和恢复策略：

| 指标 | 目标值 | 说明 |
|------|--------|------|
| RPO | < 24 小时 | 每日备份，最多丢失 24 小时向量数据 |
| RTO | < 4 小时 | 从备份恢复 + 数据重建 |

**备份执行细节：**

```bash
# 每日凌晨 2:00 执行 Milvus 快照备份
milvusctl snapshot create -c default_collection -u http://milvus:19530

# 备份存储至 MinIO
mc cp milvus_snapshots/ minio/milvus-backups/$(date +%Y%m%d)/ --recursive

# 完整性校验
milvusctl snapshot verify -p minio/milvus-backups/$(date +%Y%m%d)/
```

**恢复步骤详解（5 步流程）：**

| 步骤 | 操作 | 预计耗时 |
|------|------|----------|
| 1 | 停止 Milvus 服务 | < 1 分钟 |
| 2 | 从 MinIO 拉取最新快照 | 5-10 分钟（取决于数据量） |
| 3 | 执行快照恢复命令 `milvusctl snapshot restore` | 10-30 分钟 |
| 4 | 启动 Milvus 服务并验证集合完整性 | < 5 分钟 |
| 5 | 对缺失的向量数据进行增量重建（从 MySQL 源数据重新 embedding） | 1-2 小时 |

**数据丢失影响评估：**

| 影响维度 | 影响程度 | 说明 |
|----------|----------|------|
| 核心业务 | 无影响 | 简历原文、员工数据存储在 MySQL，不受 Milvus 故障影响 |
| 检索功能 | 暂时不可用 | 语义搜索、简历推荐功能暂停，待恢复后可用 |
| 重建耗时 | 2-4 小时 | 从 MySQL 源数据重新生成 embedding 向量 |

| 存储组件 | 用途 | 部署模式 |

## 6. 关键设计决策

### 6.1 域服务合并决策 (V15 修订)

**决策：** 将 V14 的 8 个独立 Agent 服务合并为 4 个域服务。

**背景：** V14 架构将 user-agent、cert-agent、recruit-agent、train-agent、comp-agent、perf-agent、analytics-agent、auto-agent 作为 8 个独立服务部署，导致以下问题：
1. 跨服务调用频繁（如入职流程需要 user-agent + recruit-agent + comp-agent 协作）
2. 数据分散在 8 个数据库 schema 中，一致性问题突出
3. 部署和运维成本高（8 个服务的独立配置、监控、日志）

**合并方案：**

| 域服务 | 合并来源 | 合并理由 |
|--------|----------|----------|
| 用户中心域 | user-agent + cert-agent | 员工信息和证书管理紧密相关，共享员工数据模型 |
| 招聘培训域 | recruit-agent + train-agent | 招聘和培训都属于人才发展范畴，流程连续 |
| 薪酬考勤域 | comp-agent + perf-agent | 薪资和绩效数据强相关（绩效影响薪资） |
| 分析自动化域 | analytics-agent + auto-agent | 报表生成和自动化流程天然一体 |

**影响评估：**
- 正面：减少跨服务调用 60%、降低部署复杂度、改善数据一致性
- 负面：单域服务体积增大（但仍在合理范围内，每个域 < 50 万行代码）

### 6.2 移除 Spring Cloud Gateway 决策 (V15 修订)

**决策：** 移除 Spring Cloud Gateway，采用 K8s Nginx Ingress Controller 作为统一网关。

**背景：** V14 使用 Spring Cloud Gateway 作为 API 网关，负责路由、鉴权、限流。但引入以下问题：
1. 增加一层服务跳转，增加延迟（约 50-100ms）
2. 网关成为单点故障（虽然有集群，但增加了系统复杂度）
3. 鉴权逻辑集中在网关，导致网关与业务逻辑耦合

**替代方案：**
- Nginx Ingress Controller 处理 SSL 终止和路由转发
- 鉴权（JWT 验证）、限流下沉至各 Agent 服务内部
- 好处：减少延迟、简化架构、Agent 服务自主管理安全策略

**影响评估：**
- 延迟降低：减少 50-100ms 网关跳转时间
- 复杂度降低：少维护一个网关服务
- 安全性：各服务独立管理鉴权，故障隔离更好

### 6.3 端口分配策略

**决策：** 域服务采用连续端口分配（8081-8084），共享服务使用 8085，AI 模型服务使用 8000-8003。

**理由：**
1. 连续端口便于记忆和管理
2. 端口范围划分清晰：808x 为域服务，800x 为 AI 模型服务
3. 预留 8086-8090 供未来扩展

### 6.4 本地化 AI 模型部署

**决策：** 所有 AI 模型（LLM、OCR、人脸识别、Embedding）均采用本地部署，不依赖云端 API。

**理由：**
1. **数据安全** — HR 数据包含大量个人信息（身份证、银行卡、薪资等），本地部署确保数据不出域
2. **成本可控** — 一次性硬件投入，无按量付费的不确定性
3. **延迟稳定** — 本地网络延迟 < 1ms，远低于云端 API（通常 50-200ms）
4. **可用性强** — 不依赖外部网络，避免因云端服务故障导致系统不可用

**硬件需求：**
- GPU 服务器：1× NVIDIA A100 (80GB) 用于 LLM 推理
- CPU 服务器：OCR、人脸识别、Embedding 共享一台 16 Core / 64GB RAM 服务器

### 6.5 Milvus 单节点部署

**决策：** 向量数据库 Milvus 采用单节点 Docker Compose 部署，而非集群模式。

**理由：**
1. **数据量评估** — 预计简历向量 < 100 万，文档向量 < 500 万，单节点完全满足
2. **运维简化** — 单节点部署大幅降低运维复杂度
3. **性能足够** — 单节点 Milvus 在 1000 万向量规模下检索延迟 < 100ms
4. **可扩展性** — 未来数据量增长时可平滑迁移至集群模式

**备份策略：** 每日凌晨 2:00 执行快照备份至 MinIO，详见第 2.6.2 节。

### 6.6 服务治理方案

**决策：** 采用 K8s Service + Resilience4j 应用层熔断统一管理服务间通信。

**方案组成：**

| 组件 | 职责 | 配置 |
|------|------|------|
| K8s Service | 服务发现、负载均衡 | ClusterIP 模式，DNS 解析 |
| Resilience4j | 熔断、限流、重试 | 每个下游调用独立配置 |
| OpenFeign | 声明式 HTTP 客户端 | 与 Resilience4j 集成 |

**熔断策略：**

| 指标 | 阈值 | 动作 |
|------|------|------|
| 错误率 | > 50% (10 秒窗口) | 打开熔断器，停止调用 30 秒 |
| 慢调用率 | > 80% (P95 > 2 秒) | 降级为缓存数据或默认值 |
| 调用超时 | > 5 秒 | 快速失败，记录日志 |

## 7. 分布式事务与数据一致性

### 7.1 事务场景分析

GBM AI Agent HR 系统存在以下跨服务事务场景：

| 场景 | 涉及服务 | 一致性要求 | 说明 |
|------|----------|------------|------|
| 新员工入职 | 招聘培训域 → 用户中心域 → 薪酬考勤域 | 最终一致性 | 招聘完成后创建员工档案，然后初始化薪资信息 |
| 薪资发放 | 薪酬考勤域 → 用户中心域 | 强一致性 | 薪资计算结果与员工银行账户信息必须一致 |
| 证书更新 | 用户中心域 → 招聘培训域 | 最终一致性 | 证书更新后同步到培训记录 |
| 离职流程 | 用户中心域 → 薪酬考勤域 → 招聘培训域 | 最终一致性 | 离职后停薪、归档培训记录、释放招聘名额 |

### 7.2 事务方案选型

**决策：** 采用 Saga 模式（编排式）作为主要的分布式事务方案。

**选型对比：**

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| Saga (编排式) | 中心化控制、易于追踪、补偿逻辑清晰 | 编排器成为单点 | 本系统主方案 |
| Saga (协同式) | 去中心化、灵活性高 | 追踪困难、补偿逻辑分散 | 不适用 |
| TCC | 强一致性 | 侵入业务代码、实现复杂 | 薪资发放（见 7.3 节） |
| 本地消息表 | 实现简单 | 需要额外定时任务清理 | 非关键场景备用 |

### 7.3 Saga 编排设计

**编排器：** Camunda 8 (Zeebe) 作为 Saga 编排器，利用 BPMN 流程定义事务步骤和补偿逻辑。

```
[招聘完成] → [创建员工档案] → [初始化薪资] → [发送通知]
     │              │              │              │
     │              ↓              ↓              ↓
     │         [补偿:删除档案] [补偿:重置薪资] [无需补偿]
     ↓
[补偿:撤销招聘]
```

**补偿策略：**

| 步骤 | 正常操作 | 补偿操作 | 补偿失败处理 |
|------|----------|----------|-------------|
| 创建员工档案 | 插入员工记录 | 标记为"待删除"（软删除） | 记录告警，人工介入 |
| 初始化薪资 | 插入薪资配置 | 删除薪资配置 | 记录告警，人工介入 |
| 发送通知 | 发送入职通知 | 发送取消通知 | 忽略（通知可重复） |

### 7.4 TCC 方案（薪资发放场景）

**决策：** 薪资发放场景采用 TCC (Try-Confirm-Cancel) 模式，确保强一致性。

**TCC 三阶段：**

| 阶段 | 操作 | 说明 |
|------|------|------|
| Try | 冻结薪资金额、锁定银行账户 | 预留资源，不实际转账 |
| Confirm | 执行转账、更新薪资记录 | 实际执行操作 |
| Cancel | 解冻薪资金额、释放银行账户 | 回滚预留资源 |

**实现方式：** Seata AT 模式（自动事务恢复）+ 手动 TCC 接口。

### 7.5 数据一致性保障

| 保障措施 | 实现方式 | 说明 |
|----------|----------|------|
| 幂等性 | 请求 ID 去重表 | 每个操作携带唯一请求 ID，防止重复执行 |
| 对账机制 | 定时对账任务 | 每日凌晨对账，发现不一致自动修复 |
| 审计日志 | 操作日志表 | 记录所有数据变更，支持追溯和修复 |
| 数据校验 | 入库前校验 | 关键数据（薪资、社保）入库前多重校验 |

## 8. 安全合规与数据保护

### 8.1 认证与授权

|------|----------|------|
| 认证服务 | Spring Security + JWT | 统一的认证和令牌颁发 |

| 角色 | 权限范围 | 说明 |
|------|----------|------|
| 系统管理员 | 全部 | 系统配置、用户管理、权限分配 |

### 8.2 数据传输安全

| 场景 | 加密方式 | 实现 |
|------|----------|------|
| 外部通信 | TLS 1.3 | Nginx Ingress SSL 终止 |
| 服务间通信 | mTLS | K8s Service Mesh（可选）或应用层 TLS |

### 8.3 数据存储安全

| 数据类型 | 加密方式 | 存储位置 |
|----------|----------|----------|
| 身份证号 | AES-256-GCM | MySQL (加密列) |
| 银行卡号 | AES-256-GCM | MySQL (加密列) |
| 薪资数据 | AES-256-GCM | MySQL (加密列) |
| 人脸特征 | 不可逆哈希 | MySQL (特征向量) |
| 生物识别原始数据 | 不存储 | 实时比对后立即删除 |
| 普通业务数据 | TDE (透明加密) | MySQL 表空间加密 |

**密钥管理：** HashiCorp Vault (K8s Operator 模式)

| 功能 | 实现 |
|------|------|

## 12. Agent 异常处理与补偿机制

### 12.1 异常分类

| 异常类型 | 说明 | 示例 | 处理策略 |
|----------|------|------|----------|
| 临时性异常 | 网络抖动、服务短暂不可用 | HTTP 503、数据库连接超时 | 自动重试（指数退避） |
| 永久性异常 | 数据不存在、权限不足 | HTTP 404、403 | 记录日志，通知人工 |
| 业务异常 | 业务规则不满足 | 薪资计算结果为负数 | 记录日志，触发补偿 |
| 外部系统异常 | 外部 API 不可用、RPA 目标网站变化 | 社保局网站维护 | 降级处理，定时重试 |
| AI 推理异常 | LLM 返回结果不符合预期 | OCR 识别失败 | 重试或降级至人工 |

### 12.2 重试策略

**决策：** 采用 Resilience4j Retry 实现智能重试。

| 异常类型 | 重试次数 | 退避策略 | 最大等待时间 |
|----------|----------|----------|-------------|
| 网络超时 | 3 次 | 指数退避 (1s, 2s, 4s) | 10 秒 |
| HTTP 5xx | 3 次 | 固定间隔 (2s) | 8 秒 |
| 数据库连接 | 5 次 | 指数退避 (0.5s, 1s, 2s, 4s, 8s) | 20 秒 |
| AI 推理 | 2 次 | 固定间隔 (5s) | 10 秒 |
| RPA 操作 | 3 次 | 固定间隔 (10s) | 30 秒 |

### 12.3 熔断策略

**决策：** 采用 Resilience4j CircuitBreaker 实现服务熔断。

| 下游服务 | 错误率阈值 | 滑动窗口 | 熔断持续时间 | 半开状态最大调用 |
|----------|-----------|----------|-------------|-----------------|
| OCR 服务 | 50% | 100 次 | 30 秒 | 5 次 |
| RPA 服务 | 30% | 50 次 | 60 秒 | 3 次 |
| LLM 服务 | 40% | 100 次 | 30 秒 | 5 次 |
| 人脸识别 | 50% | 100 次 | 30 秒 | 5 次 |
| 数据库 | 20% | 50 次 | 60 秒 | 3 次 |

### 12.4 补偿机制

**决策：** Saga 补偿 + 死信队列双重保障。

**Saga 补偿流程：**

```
[任务 A 成功] → [任务 B 成功] → [任务 C 失败]
                                      ↓
                               [执行 C 补偿]
                                      ↓
                               [执行 B 补偿]
                                      ↓
                               [执行 A 补偿]
                                      ↓
                               [记录补偿结果]
                               [通知人工介入（如补偿失败）]
```

**死信队列 (DLQ) 设计：**

| 队列 | 用途 | 处理策略 |
|------|------|----------|
| dlq.user-domain | 用户中心域失败消息 | 每小时重试，3 次后转人工 |
| dlq.recruit-domain | 招聘培训域失败消息 | 每小时重试，3 次后转人工 |
| dlq.payroll-domain | 薪酬考勤域失败消息 | 每小时重试，3 次后转人工 |
| dlq.auto-domain | 分析自动化域失败消息 | 每小时重试，3 次后转人工 |

### 12.5 降级模式

**决策：** 当外部依赖不可用时，系统进入降级模式保障核心业务。

| 降级场景 | 降级策略 | 影响范围 |
|----------|----------|----------|
| LLM 服务不可用 | 使用规则引擎替代 AI 推理 | 简历筛选降级为关键词匹配 |
| OCR 服务不可用 | 暂停证件自动识别，允许后续补录 | 入职办理延迟，但不阻塞 |
| RPA 服务不可用 | 暂停外务自动操作，生成待办清单 | 社保/公积金操作延迟 |
| 人脸服务不可用 | 暂停人脸比对，使用证件号校验 | 签到功能降级 |
| 向量检索不可用 | 使用关键词检索替代 | 简历推荐精度下降 |

**降级例外条款（与 SRS 8.3 节一致）：**
- 降级期间的所有人工操作需完整记录至审计日志
- 降级原因和持续时间需纳入月度运维报告
- 降级因素消除后应立即恢复全自动化模式

### 12.6 告警机制

| 告警级别 | 触发条件 | 通知方式 | 响应时间 |
|----------|----------|----------|----------|
| P0 (紧急) | 核心服务不可用、数据丢失 | 电话 + 短信 + 邮件 | 15 分钟内 |
| P1 (高) | 服务性能下降 > 50%、熔断触发 | 短信 + 邮件 | 30 分钟内 |
| P2 (中) | 重试次数超限、死信队列积压 | 邮件 + 钉钉/企微 | 2 小时内 |
| P3 (低) | 常规异常、日志警告 | 邮件 | 24 小时内 |

## 13. 多租户隔离策略

### 13.1 多租户需求分析

**决策：** GBM AI Agent HR 系统当前为单租户部署，但架构设计预留多租户扩展能力。

**理由：**
1. GBM 为单一企业部署，当前无需多租户
2. 未来可能扩展为 SaaS 模式服务于多家企业
3. 预留多租户能力可降低未来改造成本

### 13.2 多租户架构设计（预留方案）

**隔离级别：** 数据库 Schema 隔离（逻辑隔离）

| 隔离级别 | 实现方式 | 优点 | 缺点 | 适用场景 |
|----------|----------|------|------|----------|
| 数据库隔离 | 每个租户独立数据库 | 最高隔离性 | 成本高 | 高端 SaaS |
| Schema 隔离 | 每个租户独立 Schema | 较高隔离性 | 中等成本 | 本系统预留方案 |
| 字段隔离 | 共享表，tenant_id 字段区分 | 成本最低 | 隔离性弱 | 低端 SaaS |

### 13.3 租户标识设计

**租户 ID 规则：** `TENANT` + `6 位数字`

| 租户 | 租户 ID | 说明 |
|------|---------|------|
| GBM (当前) | TENANT000001 | 默认租户 |

**实现方式：**

| 组件 | 实现 |
|------|------|
| 请求识别 | HTTP 头 `X-Tenant-ID` |
| 数据库路由 | MyBatis-Plus 插件自动注入 tenant_id |
| 缓存隔离 | Redis Key 前缀 `tenant:{tenant_id}:` |
| 文件隔离 | MinIO 路径 `/tenants/{tenant_id}/` |

### 13.4 租户数据迁移方案

| 场景 | 迁移方式 | 说明 |
|------|----------|------|
| 新增租户 | 自动创建 Schema + 初始化数据 | 部署脚本自动执行 |
| 租户数据导出 | 全量导出为 SQL + 文件包 | 用于备份或迁移 |
| 租户删除 | 软删除（标记为禁用） | 保留数据 30 天后可恢复 |

## 14. Agent 间通信机制

### 14.1 通信方式

| 通信方式 | 使用场景 | 协议 | 说明 |
|----------|----------|------|------|
| 同步调用 | 需要即时结果的场景 | HTTP/REST (OpenFeign) | 如薪资查询、员工信息获取 |
| 异步消息 | 事件通知、流程推进 | Kafka | 如招聘完成通知、薪资发放完成 |
| 事件发布 | 状态变更通知 | Kafka (发布-订阅) | 如员工入职、离职事件 |

### 14.2 同步调用设计

**决策：** 采用 OpenFeign + Resilience4j 进行同步服务调用。

```
[用户中心域] --(HTTP/REST)--> [薪酬考勤域]
    ↓ OpenFeign 客户端
    ↓ Resilience4j 熔断
    ↓ 超时 5 秒
[返回员工基本信息]
```

**调用规范：**

| 规范项 | 规则 |
|--------|------|
| 超时时间 | 默认 5 秒，复杂查询 10 秒 |
| 重试策略 | 仅对幂等操作重试（GET 请求） |
| 熔断策略 | 错误率 > 50% 触发熔断 |
| 请求格式 | JSON (application/json) |
| 响应格式 | 统一响应包装 `{code, message, data}` |

### 14.3 异步消息设计

**决策：** 采用 Kafka 作为异步消息总线。

**Topic 设计：**

| Topic | 用途 | 分区数 | 保留时间 |
|-------|------|--------|----------|
| hr.employee.events | 员工事件（入职、离职、转岗） | 6 | 30 天 |
| hr.recruit.events | 招聘事件（简历投递、面试安排） | 4 | 30 天 |
| hr.payroll.events | 薪资事件（薪资计算完成、发放完成） | 4 | 30 天 |
| hr.attendance.events | 考勤事件（打卡记录、异常） | 4 | 7 天 |
| hr.training.events | 培训事件（培训计划、签到、成绩） | 4 | 30 天 |
| hr.cert.events | 证书事件（到期提醒、续期） | 2 | 30 天 |
| hr.performance.events | 绩效事件（目标设定、评分完成） | 4 | 30 天 |

**消息格式：**

```json
{
  "event_id": "evt_20260615_001",
  "event_type": "employee.onboarded",
  "timestamp": "2026-06-15T10:30:00Z",
  "source_service": "user-domain",
  "data": {
    "emp_no": "EMP20260001",
    "emp_name": "张三",
    "dept_code": "DEPT001",
    "entry_date": "2026-06-15"
  }
}
```

### 14.4 消息可靠性保障

| 保障措施 | 实现方式 |
|----------|----------|
| 生产端确认 | acks=all, retry=3 |
| 消费端确认 | 手动 ACK，处理完成后确认 |
| 消息顺序 | 同一员工消息使用 emp_no 作为分区键 |
| 死信队列 | 消费失败 3 次后转入 DLQ |
| 消息追踪 | 消息头注入 TraceContext |

```
                              3. 分配员工编号
                                       ↓
                              [用户中心域] 发布员工创建事件
                                       ↓
                              [Kafka: hr.employee.events]
                                       ↓
                              [薪酬考勤域] 消费事件
                                       ↓
                              1. 初始化薪资配置
                              2. 设置社保/公积金账户
                                       ↓
                              [薪酬考勤域] 发布薪资初始化事件
                                       ↓
                              [Kafka: hr.payroll.events]
                                       ↓
                              [分析自动化域] 消费事件
                                       ↓
                              更新招聘效果统计数据
```

**2. 薪资发放数据流：**

```
[薪酬考勤域] ──薪资计算完成──→ [Kafka: hr.payroll.events]
                                      ↓
                             [薪酬考勤域] 内部 TCC 事务
                                      ↓
                             1. Try: 冻结薪资金额
                             2. Confirm: 执行转账
                             3. 发布发放完成事件
                                      ↓
                             [Kafka: hr.payroll.events]
                                      ↓
                             [用户中心域] 消费事件
                                      ↓
                             更新员工薪资记录
                                      ↓
                             [分析自动化域] 消费事件
                                      ↓
                             更新财务报表
```

**3. 离职流程数据流：**

```
[用户中心域] ──离职申请──→ [Kafka: hr.employee.events]
                                 ↓
                        [用户中心域] 启动离职流程
                                 ↓
                        1. 生成交接清单
                        2. 通知相关部门
                                 ↓
                        [用户中心域] 发布离职进行中事件
                                 ↓
                        [Kafka: hr.employee.events]
                                 ↓
                        [薪酬考勤域] 消费事件
                                 ↓
                        1. 计算最后薪资
                        2. 停止社保/公积金
                                 ↓
                        [招聘培训域] 消费事件
                                 ↓
                        1. 归档培训记录
                        2. 释放招聘名额
                                 ↓
                        [用户中心域] 完成离职
                                 ↓
                        1. 更新员工状态
                        2. 归档员工档案
```

### 15.2 数据流监控

| 监控指标 | 监控方式 | 告警阈值 |
|----------|----------|----------|
| 消息堆积 | Kafka Consumer Lag | 单分区 > 10 万条 |
| 处理延迟 | 消息时间戳 vs 处理时间戳 | P95 > 5 秒 |
| 处理失败率 | 失败消息数 / 总消息数 | > 1% |
| 数据一致性 | 定时对账任务 | 差异 > 0 |

### 15.3 数据流幂等性

| 场景 | 幂等键 | 实现方式 |
|------|--------|----------|
| 员工创建 | emp_no | 唯一索引 + 请求 ID 去重表 |
| 薪资发放 | salary_batch_no | 批次号唯一索引 |
| 考勤记录 | emp_no + date + type | 复合唯一索引 |
| 培训签到 | training_no + emp_no | 复合唯一索引 |

## 17. 国际化(i18n/l10n)架构设计

### 17.1 国际化需求

**决策：** GBM AI Agent HR 系统当前为中文单语言部署，但架构预留国际化扩展能力。

**理由：**
1. GBM 为中国企业，当前仅需中文
2. 未来可能扩展至海外分支机构
3. 预留国际化能力可降低未来改造成本

### 17.2 国际化架构设计

**技术选型：** Spring Boot 原生国际化 + Vue i18n

| 层级 | 技术选型 | 说明 |
|------|----------|------|
| 后端 | Spring MessageSource | .properties/.yaml 资源文件 |
| 前端 | Vue i18n | JSON 语言包 |
| 数据库 | 多语言字段扩展 | 预留 translation 表 |

### 17.3 语言包管理

**后端语言包目录：**

```
src/main/resources/i18n/
├── messages.properties          # 默认（中文）
├── messages_en.properties       # 英文
└── messages_ja.properties       # 日文（预留）
```

**前端语言包目录：**

```
src/locales/
├── zh-CN.json                   # 简体中文
├── en-US.json                   # 英文
└── ja-JP.json                   # 日文（预留）
```

### 17.4 语言切换机制

| 切换方式 | 实现 | 说明 |
|----------|------|------|
| URL 参数 | `/api/zh-CN/...` vs `/api/en-US/...` | 后端 API 语言切换 |
| HTTP 头 | `Accept-Language: zh-CN` | 标准语言协商 |
| 用户偏好 | 用户配置文件存储语言偏好 | 持久化用户选择 |
| 前端切换 | Vue i18n `locale` 动态切换 | 无需刷新页面 |

### 17.5 日期/时间/货币格式化

| 类型 | 中文 (zh-CN) | 英文 (en-US) |
|------|-------------|-------------|
| 日期 | 2026-06-15 | 06/15/2026 |
| 时间 | 14:30:00 | 2:30:00 PM |
| 货币 | ¥15,000.00 | $15,000.00 |
| 数字 | 1,000,000 | 1,000,000 |

**实现：** Java `java.time.format.DateTimeFormatter` + `java.text.NumberFormat`，前端使用 `Intl` API。

### 17.6 数据库国际化扩展

**预留翻译表结构：**

```sql
CREATE TABLE translation (
    id BIGINT PRIMARY KEY,
    resource_type VARCHAR(50),     -- 资源类型 (department, position, etc.)
    resource_id BIGINT,            -- 资源 ID
    locale VARCHAR(10),            -- 语言代码 (zh-CN, en-US)
    content TEXT,                  -- 翻译内容
    create_time DATETIME,
    update_time DATETIME,
    UNIQUE KEY uk_translation (resource_type, resource_id, locale)
);
```

## 18. 无障碍访问架构设计

### 18.1 无障碍需求

**决策：** GBM AI Agent HR 系统遵循 WCAG 2.1 AA 级无障碍标准，确保残障人士可使用系统。

**理由：**
1. 《中华人民共和国无障碍环境建设法》要求
2. 企业社会责任
3. 扩大系统用户覆盖面

### 18.2 无障碍架构设计

**前端无障碍：**

| 标准 | 实现方式 | 说明 |
|------|----------|------|
| WCAG 2.1 AA | Vue 3 组件遵循 ARIA 标准 | 所有交互元素添加 ARIA 属性 |
| 键盘导航 | Tab 键完整导航 | 所有功能可通过键盘操作 |
| 屏幕阅读器 | 语义化 HTML + ARIA 标签 | 支持 NVDA、VoiceOver 等 |
| 颜色对比度 | 最小对比度 4.5:1 | 确保色盲用户可辨识 |
| 字体缩放 | 支持 200% 字体放大 | 不影响页面布局 |

**后端无障碍：**

| 功能 | 实现方式 | 说明 |
|------|----------|------|
| 文档无障碍 | 生成的 PDF/Word 遵循 PDF/UA 标准 | 屏幕阅读器可读取 |
| 邮件无障碍 | 邮件内容遵循邮件无障碍标准 | _alt_ 标签、简洁布局 |
| 短信无障碍 | 简洁明了的短信内容 | 避免复杂格式 |

### 18.3 无障碍测试

| 测试类型 | 工具 | 频率 |
|----------|------|------|
| 自动化测试 | axe-core (Vue 插件) | 每次构建 |
| 手动测试 | WAVE、Lighthouse | 每次发布前 |
| 用户测试 | 邀请残障用户测试 | 每季度 |

### 18.4 无障碍组件库

**决策：** 使用 Element Plus 无障碍组件 + 自定义无障碍组件。

| 组件 | 无障碍特性 | 说明 |
|------|----------|------|
| 按钮 | `role="button"`, 键盘焦点 | 默认支持 |
| 表单 | `aria-label`, `aria-required` | 需手动配置 |
| 表格 | `scope`, `caption` | 需手动配置 |
| 弹窗 | `role="dialog"`, 焦点管理 | 需手动配置 |
| 导航 | `role="navigation"`, 跳过链接 | 需手动配置 |

### 18.5 无障碍监控

| 监控指标 | 监控方式 | 目标值 |
|----------|----------|--------|
| 无障碍合规率 | axe-core 扫描 | 100% 无严重问题 |
| 键盘导航覆盖率 | 手动测试 | 100% 功能可键盘操作 |
| 屏幕阅读器兼容性 | 用户测试 | 主要功能可用 |
| 颜色对比度 | Lighthouse 扫描 | 所有文本 ≥ 4.5:1 |
