## 1. 架构概述

### 1.1 设计目标

GBM AI Agent HR 系统采用 **AI 原生模块化单体 (Modular Monolith) 架构**，以 AI Agent 为系统核心执行主体，实现人力资源管理全流程的自动化。所有业务模块运行在单一 JVM 进程中（端口 8080），通过清晰的模块边界和内聚的领域模型保证代码可维护性。架构设计遵循以下原则：

1. **零操作性原则** — 所有操作性事务由 Agent 自主完成，人类仅承担审核与仲裁
2. **模块化单体** — 按业务域划分为 **4 个逻辑模块**（用户中心模块、招聘培训模块、薪酬考勤模块、分析自动化模块），运行在单一 JVM 中。模块间通过包内方法调用（同步）或 Spring Event + Redis Stream（异步事件）通信，避免微服务过度拆分带来的运维复杂度（V20 修订）
3. **事件驱动** — 模块间通过 Spring Event（进程内）和 Redis Stream（进程间/跨实例）进行异步通信（V20 修订）
4. **配置驱动** — 业务规则（薪资、考勤、筛选权重）以配置形式管理
5. **可观测性** — 完整的链路追踪（OpenTelemetry + Jaeger，详见第 2.4.1 节）、日志、监控
6. **服务治理** — 通过 Resilience4j 应用层熔断统一管理外部依赖调用，模块间通过包内方法调用，不需要 Feign（V20 修订）

| 资源维度 | 触发条件 | 扩展动作 | 预期效果 |

## 2. 分层架构设计

### 2.1 展示层 (Presentation Layer)

展示层负责用户交互界面和消息推送，包含以下组件：

| 组件 | 技术选型 | 职责 |
|------|----------|------|
| Web 应用 | React 18 + Ant Design 5 | HR 审核面板、数据查看、报表展示 |
| 移动端 | PWA (React 18 + workbox 7.x) | 移动端审核、通知接收、扫码入口 |
| 扫码入口 | H5 (React 18) | 面试签到、培训签到、访客登记 |
| 通知推送 | 短信网关 + 邮件服务 | 审核通知、提醒、状态变更通知 |

**技术栈详情 (V20 修订)：**

| 用途 | 技术选择 | 版本 | 选型理由 |
|------|----------|------|----------|
| 前端框架 | React 18 | 18.x | 成熟生态、组件化、Hooks 范式 |
| UI 组件库 | Ant Design | 5.x | 企业级组件库、与 React 生态深度集成 |
| 状态管理 | Zustand + @tanstack/react-query | 4.x + 5.x | 轻量状态管理 + 服务端状态缓存 |
| 路由 | React Router | 6.x | React 生态标准路由方案 |
| 构建工具 | Vite | 5.x | 快速冷启动、HMR 热更新 |
| 语言 | TypeScript | - | 类型安全、IDE 智能提示 |
| HTTP 客户端 | Axios | 1.7.x | 成熟稳定、拦截器机制 |
| 移动端方案 | PWA + workbox | 7.x | 一套代码多端、离线支持、推送通知 |

**设计说明：** 展示层仅提供"查看"和"审核"功能，不提供操作性功能。所有数据录入、资料整理、表单填写等操作均由 Agent 完成。移动端采用 PWA 方案替代原 UniApp 方案（V20 修订），通过 workbox 实现离线缓存和推送通知。

### 2.2 网关层 (Gateway Layer)

V15 修订：移除 Spring Cloud Gateway，采用 K8s Nginx Ingress Controller 作为统一入口。

```
                    互联网
                      |
              +-------+-------+
              |  K8s Ingress  |
              |  Controller   |
              +---------------+
              |               |
    +---------+         +-----+--------+
    | Nginx (L7) |       | Nginx (L7)  |
    +---------+         +-----+--------+
              |               |
    +---------+-------+ +-----+--------+
    |  static.resources |  /api/* routes |
    +-------------------+ +--------------+
```

**职责划分：**
- SSL 证书终止、路由转发、静态资源服务由 Nginx Ingress 处理
- 鉴权（JWT 验证）、限流、请求日志下沉至 Agent 服务内部处理
- 好处：减少一层服务跳转，降低延迟；Agent 服务自主管理安全策略

### 2.3 编排调度层 (Orchestration Layer)

```
+---------------------------------------------------------------+
|                    Flowable 7.0.x                              |
|  +------------------+  +------------------+  +--------------+ |
|  | BPMN 流程定义    |  | 并行网关 (Parallel)|  | 排他网关     | |
|  | (招聘流程、入职   |  |  (证件识别并行     |  | (审核/驳回)  | |
|  |   流程、离职流程) |  |    人脸比对等)    |  |              | |
|  +------------------+  +------------------+  +--------------+ |
|  +---------------------------------------------------------+ |
|  |  模块内 BPMN 流程 — 每个业务模块注册为 Flowable Task      | |
|  |  任务类型：简历筛选、证件识别、薪资计算、RPA 操作等        | |
|  +---------------------------------------------------------+ |
+---------------------------------------------------------------+
```

**核心组件：**

1. **流程定义引擎 (Flowable 7.0.x)**
   - 基于 BPMN 2.0 标准定义业务流程
   - 支持并行网关（如证件识别并行执行）、排他网关（审核通过/驳回）
   - 流程版本管理，支持灰度发布
   - 与 Spring Boot 原生集成，嵌入在单体应用内部（V20 修订）

2. **任务分解器 (Task Decomposer)**
   - 将复杂任务（如"入职办理"）分解为子任务
   - 子任务映射到对应的 Agent 模块
   - 支持任务优先级和依赖关系管理

3. **状态管理器 (State Manager)**
   - Redis 存储流程实例状态（TTL = 30 天）
   - MySQL 持久化流程历史（用于审计和追溯）
   - 支持断点恢复：Agent 失败后可从上一个检查点继续

### 2.4 域服务层 (Domain Services Layer)

4 个业务模块是系统的核心业务执行层，每个模块内部包含多个 Agent 子模块，运行在单一 JVM 进程中。

#### 2.4.1 链路追踪设计

全系统采用 OpenTelemetry 进行分布式链路追踪：

```
User Request → Ingress → [TraceID] → Application :8080 → [SpanID] →
  → Redis Stream Event → [TraceID] → Downstream Module → [SpanID]
```

| 组件 | 追踪方式 | 实现 |
|------|----------|------|
| HTTP 请求 | W3C Trace Context 头 | OpenTelemetry Java Agent |
| Redis Stream 消息 | 消息元数据注入 TraceContext | Redis Stream Tracing Interceptor |
| 数据库查询 | SQL 查询 Span | OpenTelemetry JDBC Instrumentation |
| Agent 任务 | 自定义 Span | Flowable 原生 Trace ID 集成 |

**链路追踪数据存储：** Jaeger (All-in-one 模式，单节点部署)

### 2.5 共享基础设施层 (Shared Infrastructure)

V20 修订：OCR、RPA、文件处理服务整合入单体应用内部，不再作为独立服务部署。

| 服务 | 部署方式 | 职责 | 调用方 |
|------|----------|------|--------|
| OCR 服务 | 单体内模块 | 身份证、学历证、银行卡识别 | 用户中心模块、招聘培训模块 |
| RPA 服务 | 单体内模块 | 社保局、公积金网站自动化操作 | 薪酬考勤模块、用户中心模块 |
| 文件处理 | 单体内模块 | 文档合并、PDF 生成、图片压缩 | 所有模块 |

**设计说明：** OCR、RPA、文件处理作为共享基础设施能力，整合入单体应用内部（V20 修订）。所有业务模块通过包内方法调用直接使用这些能力，减少了网络开销和部署复杂度。

### 2.6 AI 模型服务层 (AI Model Services)

| 模型服务 | 技术选型 | 部署方式 | 资源需求 |
|----------|----------|----------|----------|
| LLM 推理 | vLLM + Qwen-72B-AWQ | 本地 GPU 服务器 | 1× NVIDIA A100 (80GB) |
| OCR 推理 | PaddleOCR | 本地 CPU 服务器 | 4 Core, 8GB RAM |
| 人脸服务 | face_recognition (dlib) | 本地 CPU 服务器 | 4 Core, 8GB RAM |
| Embedding | bge-m3 | 本地 CPU 服务器 | 2 Core, 4GB RAM |

**RPO/RTO 保障方案 (2.6.1)：**

| 模型服务 | RPO (数据丢失) | RTO (恢复时间) | 保障措施 |
|----------|----------------|----------------|----------|
| vLLM | 模型权重不丢失（只读） | < 30 分钟 | Docker 容器重启 + 模型缓存预热 |
| PaddleOCR | 不丢失（只读模型） | < 15 分钟 | 容器重启即恢复 |
| face_recognition | 不丢失（只读模型） | < 15 分钟 | 容器重启即恢复 |
| bge-m3 | 不丢失（只读模型） | < 10 分钟 | 容器重启即恢复 |

**Milvus 单节点 RPO/RTO 保障方案 (2.6.2)：**

由于向量数据（简历嵌入、文档嵌入等）属于可重建数据，Milvus 单节点采用以下备份和恢复策略：

| 指标 | 目标值 | 说明 |
|------|--------|------|
| RPO | < 24 小时 | 每日备份，最多丢失 24 小时向量数据 |
| RTO | < 4 小时 | 从备份恢复 + 数据重建 |

**备份执行细节：**

```bash
# 每日凌晨 2:00 执行 Milvus 快照备份
milvusctl snapshot create -c default_collection -u http://milvus:19530

# 备份存储至 MinIO
mc cp milvus_snapshots/ minio/milvus-backups/$(date +%Y%m%d)/ --recursive

# 完整性校验
milvusctl snapshot verify -p minio/milvus-backups/$(date +%Y%m%d)/
```

**恢复步骤详解（5 步流程）：**

| 步骤 | 操作 | 预计耗时 |
|------|------|----------|
| 1 | 停止 Milvus 服务 | < 1 分钟 |
| 2 | 从 MinIO 拉取最新快照 | 5-10 分钟（取决于数据量） |
| 3 | 执行快照恢复命令 `milvusctl snapshot restore` | 10-30 分钟 |
| 4 | 启动 Milvus 服务并验证集合完整性 | < 5 分钟 |
| 5 | 对缺失的向量数据进行增量重建（从 MySQL 源数据重新 embedding） | 1-2 小时 |

**数据丢失影响评估：**

| 影响维度 | 影响程度 | 说明 |
|----------|----------|------|
| 核心业务 | 无影响 | 简历原文、员工数据存储在 MySQL，不受 Milvus 故障影响 |
| 检索功能 | 暂时不可用 | 语义搜索、简历推荐功能暂停，待恢复后可用 |
| 重建耗时 | 2-4 小时 | 从 MySQL 源数据重新生成 embedding 向量 |

## 6. 关键设计决策

### 6.1 模块化单体架构决策 (V20 修订)

**决策：** 采用模块化单体 (Modular Monolith) 架构，所有业务模块运行在单一 JVM 进程中（端口 8080）。

**背景：** V19 采用 AI 原生微服务架构，将 4 个域服务独立部署（端口 8081-8084），通过 Kafka 集群进行异步通信，使用 OpenFeign 进行同步调用。但存在以下问题：
1. 250 并发用户的规模下，微服务架构的运维复杂度过高
2. 跨服务调用引入网络延迟和故障点（Kafka 3 节点集群、OpenFeign 调用链）
3. 分布式事务（Saga + TCC）实现复杂，数据一致性保障成本高
4. 独立部署 4 个域服务 + Kafka + Camunda 8，运维资源消耗大

**模块化单体方案：**

| 维度 | 微服务方案 (V19) | 模块化单体方案 (V20) |
|------|-----------------|---------------------|
| 部署形态 | 4 个独立进程 (8081-8084) | 单一 JVM 进程 (8080) |
| 模块间同步调用 | OpenFeign + HTTP | 包内方法调用 |
| 模块间异步通信 | Kafka 3 节点集群 | Spring Event + Redis Stream |
| 流程引擎 | Camunda 8 (Zeebe 独立部署) | Flowable 7 (嵌入单体) |
| 分布式事务 | Saga + TCC (跨服务) | 本地事务 + 事件最终一致性 |
| 运维复杂度 | 高（多服务、多中间件） | 低（单一应用） |

**模块边界保障：** 虽然运行在同一进程，但通过以下机制保障模块独立性：
- 包级访问控制（package-private 限制跨模块直接访问）
- 模块间通过明确的接口契约通信
- 模块间异步事件通过 Spring Event + Redis Stream 解耦
- 每个模块拥有独立的数据库 Schema

**影响评估：**
- 正面：大幅降低运维复杂度、消除跨服务网络延迟、简化分布式事务、减少资源消耗
- 负面：水平扩展能力受限（但可通过多副本 + Redis Session 共享解决）

### 6.2 移除 Spring Cloud Gateway 决策 (V15 修订)

**决策：** 移除 Spring Cloud Gateway，采用 K8s Nginx Ingress Controller 作为统一网关。

**背景：** V14 使用 Spring Cloud Gateway 作为 API 网关，负责路由、鉴权、限流。但引入以下问题：
1. 增加一层服务跳转，增加延迟（约 50-100ms）
2. 网关成为单点故障（虽然有集群，但增加了系统复杂度）
3. 鉴权逻辑集中在网关，导致网关与业务逻辑耦合

**替代方案：**
- Nginx Ingress Controller 处理 SSL 终止和路由转发
- 鉴权（JWT 验证）、限流下沉至各 Agent 服务内部
- 好处：减少延迟、简化架构、Agent 服务自主管理安全策略

**影响评估：**
- 延迟降低：减少 50-100ms 网关跳转时间
- 复杂度降低：少维护一个网关服务
- 安全性：各服务独立管理鉴权，故障隔离更好

### 6.3 端口分配策略 (V20 修订)

**决策：** 应用服务统一使用 8080 端口，AI 模型服务使用 8000-8003。

**理由：**
1. 模块化单体架构，单一入口端口便于管理和维护
2. 端口范围划分清晰：8080 为应用服务，800x 为 AI 模型服务
3. 预留 8086-8090 供未来扩展

### 6.4 本地化 AI 模型部署

**决策：** 所有 AI 模型（LLM、OCR、人脸识别、Embedding）均采用本地部署，不依赖云端 API。

**理由：**
1. **数据安全** — HR 数据包含大量个人信息（身份证、银行卡、薪资等），本地部署确保数据不出域
2. **成本可控** — 一次性硬件投入，无按量付费的不确定性
3. **延迟稳定** — 本地网络延迟 < 1ms，远低于云端 API（通常 50-200ms）
4. **可用性强** — 不依赖外部网络，避免因云端服务故障导致系统不可用

**硬件需求：**
- GPU 服务器：1× NVIDIA A100 (80GB) 用于 LLM 推理
- CPU 服务器：OCR、人脸识别、Embedding 共享一台 16 Core / 64GB RAM 服务器

### 6.5 Milvus 单节点部署

**决策：** 向量数据库 Milvus 采用单节点 Docker Compose 部署，而非集群模式。

**理由：**
1. **数据量评估** — 预计简历向量 < 100 万，文档向量 < 500 万，单节点完全满足
2. **运维简化** — 单节点部署大幅降低运维复杂度
3. **性能足够** — 单节点 Milvus 在 1000 万向量规模下检索延迟 < 100ms
4. **可扩展性** — 未来数据量增长时可平滑迁移至集群模式

**备份策略：** 每日凌晨 2:00 执行快照备份至 MinIO，详见第 2.6.2 节。

### 6.6 服务治理方案 (V20 修订)

**决策：** 模块间通过包内方法调用（不需要 Feign），外部依赖调用通过 Resilience4j 应用层熔断管理。

**方案组成：**

| 组件 | 职责 | 配置 |
|------|------|------|
| 包内方法调用 | 模块间同步通信 | 直接 Java 方法调用，零网络开销 |
| Resilience4j | 熔断、限流、重试（外部依赖） | 每个外部调用独立配置 |

**说明：** 由于采用模块化单体架构，模块间通过包内方法调用通信，不需要 OpenFeign（V20 修订）。Resilience4j 仅用于保护对外部系统的调用（AI 模型服务、MinIO、外部 API 等）。

**熔断策略（外部依赖）：**

| 指标 | 阈值 | 动作 |
|------|------|------|
| 错误率 | > 50% (10 秒窗口) | 打开熔断器，停止调用 30 秒 |
| 慢调用率 | > 80% (P95 > 2 秒) | 降级为缓存数据或默认值 |
| 调用超时 | > 5 秒 | 快速失败，记录日志 |

### 6.7 流程引擎选型决策 (V20 修订)

**决策：** 采用 Flowable 7.0.x 作为 BPMN 流程引擎，嵌入在单体应用内部。

**选型对比：**

| 方案 | 优点 | 缺点 | 适配性 |
|------|------|------|--------|
| Flowable 7.0.x | Spring Boot 原生嵌入、模块化单体适配、成熟稳定 | 无独立 Cloud 版本 | 本系统主方案 |
| Camunda 8 (Zeebe) | Cloud 原生、Worker 模式 | 需要独立 Zeebe 集群、微服务适配 | 不适合单体架构 |
| Activiti | 老牌成熟 | 功能有限、社区活跃度下降 | 不适用 |

### 6.8 密钥管理方案 (V20 修订)

**决策：** 采用 .env 文件方案管理敏感配置，不引入 HashiCorp Vault。

**理由：**
1. **规模适配** — 250 用户规模的系统，.env 文件方案足以满足需求
2. **运维简化** — 避免引入 HashiCorp Vault 带来的额外运维复杂度
3. **安全性保障** — 结合 K8s Secret 挂载 .env 文件，敏感信息不硬编码在代码中

**实现方式：**
- 应用配置通过 .env 文件管理，通过 K8s Secret 挂载
- 敏感字段（数据库密码、加密密钥等）存储在 .env 中
- 应用启动时通过 Spring Boot 的 `.env` 加载机制读取

## 7. 分布式事务与数据一致性

### 7.1 事务场景分析

GBM AI Agent HR 系统存在以下跨模块事务场景：

| 场景 | 涉及模块 | 一致性要求 | 说明 |
|------|----------|------------|------|
| 新员工入职 | 招聘培训模块 → 用户中心模块 → 薪酬考勤模块 | 最终一致性 | 招聘完成后创建员工档案，然后初始化薪资信息 |
| 薪资发放 | 薪酬考勤模块 → 用户中心模块 | 强一致性 | 薪资计算结果与员工银行账户信息必须一致 |
| 证书更新 | 用户中心模块 → 招聘培训模块 | 最终一致性 | 证书更新后同步到培训记录 |
| 离职流程 | 用户中心模块 → 薪酬考勤模块 → 招聘培训模块 | 最终一致性 | 离职后停薪、归档培训记录、释放招聘名额 |

### 7.2 事务方案选型 (V20 修订)

**决策：** 由于采用模块化单体架构，事务方案大幅简化。

**选型对比：**

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| 本地事务 | 强一致性、简单可靠 | 仅适用于单模块 | 模块内操作主方案 |
| Spring Event + 事务同步 | 模块间最终一致性 | 异步、延迟 | 跨模块事件主方案 |
| TCC | 强一致性 | 侵入业务代码 | 薪资发放（见 7.4 节） |
| 本地消息表 | 实现简单 | 需要额外定时任务 | 非关键场景备用 |

### 7.3 跨模块事务设计 (V20 修订)

**方案：** 采用 Spring Event（进程内事件）+ 事务同步发布器 (TransactionSynchronizationManager) 实现模块间最终一致性。

```
[招聘完成] → [Spring Event: 招聘完成事件] → [创建员工档案]
    │                                                    │
    │                                              [Redis Stream: 员工创建事件]
    │                                                    │
    │                                              [初始化薪资]
    │                                                    │
    │                                              [发送通知]
```

**事务同步机制：**
1. 源模块在本地事务中执行核心操作
2. 通过 TransactionSynchronizationManager 在事务提交后发布 Spring Event
3. 事件监听器同步处理同进程内的下游操作
4. 如需跨实例通知，监听器同时写入 Redis Stream

**补偿策略：**

| 步骤 | 正常操作 | 补偿操作 | 补偿失败处理 |
|------|----------|----------|-------------|
| 创建员工档案 | 插入员工记录 | 标记为"待删除"（软删除） | 记录告警，人工介入 |
| 初始化薪资 | 插入薪资配置 | 删除薪资配置 | 记录告警，人工介入 |
| 发送通知 | 发送入职通知 | 发送取消通知 | 忽略（通知可重复） |

### 7.4 TCC 方案（薪资发放场景）

**决策：** 薪资发放场景采用 TCC (Try-Confirm-Cancel) 模式，确保强一致性。

**TCC 三阶段：**

| 阶段 | 操作 | 说明 |
|------|------|------|
| Try | 冻结薪资金额、锁定银行账户 | 预留资源，不实际转账 |
| Confirm | 执行转账、更新薪资记录 | 实际执行操作 |
| Cancel | 解冻薪资金额、释放银行账户 | 回滚预留资源 |

**实现方式：** 手动 TCC 接口 + 本地事务保障。

### 7.5 数据一致性保障

| 保障措施 | 实现方式 | 说明 |
|----------|----------|------|
| 幂等性 | 请求 ID 去重表 | 每个操作携带唯一请求 ID，防止重复执行 |
| 对账机制 | 定时对账任务 | 每日凌晨对账，发现不一致自动修复 |
| 审计日志 | 操作日志表 | 记录所有数据变更，支持追溯和修复 |
| 数据校验 | 入库前校验 | 关键数据（薪资、社保）入库前多重校验 |

## 12. Agent 异常处理与补偿机制

### 12.1 异常分类

| 异常类型 | 说明 | 示例 | 处理策略 |
|----------|------|------|----------|
| 临时性异常 | 网络抖动、服务短暂不可用 | HTTP 503、数据库连接超时 | 自动重试（指数退避） |
| 永久性异常 | 数据不存在、权限不足 | HTTP 404、403 | 记录日志，通知人工 |
| 业务异常 | 业务规则不满足 | 薪资计算结果为负数 | 记录日志，触发补偿 |
| 外部系统异常 | 外部 API 不可用、RPA 目标网站变化 | 社保局网站维护 | 降级处理，定时重试 |
| AI 推理异常 | LLM 返回结果不符合预期 | OCR 识别失败 | 重试或降级至人工 |

### 12.2 重试策略

**决策：** 采用 Resilience4j Retry 实现智能重试。

| 异常类型 | 重试次数 | 退避策略 | 最大等待时间 |
|----------|----------|----------|-------------|
| 网络超时 | 3 次 | 指数退避 (1s, 2s, 4s) | 10 秒 |
| HTTP 5xx | 3 次 | 固定间隔 (2s) | 8 秒 |
| 数据库连接 | 5 次 | 指数退避 (0.5s, 1s, 2s, 4s, 8s) | 20 秒 |
| AI 推理 | 2 次 | 固定间隔 (5s) | 10 秒 |
| RPA 操作 | 3 次 | 固定间隔 (10s) | 30 秒 |

### 12.3 熔断策略

**决策：** 采用 Resilience4j CircuitBreaker 实现服务熔断。

| 下游服务 | 错误率阈值 | 滑动窗口 | 熔断持续时间 | 半开状态最大调用 |
|----------|-----------|----------|-------------|-----------------|
| OCR 服务 | 50% | 100 次 | 30 秒 | 5 次 |
| RPA 服务 | 30% | 50 次 | 60 秒 | 3 次 |
| LLM 服务 | 40% | 100 次 | 30 秒 | 5 次 |
| 人脸识别 | 50% | 100 次 | 30 秒 | 5 次 |
| 数据库 | 20% | 50 次 | 60 秒 | 3 次 |

### 12.4 补偿机制 (V20 修订)

**决策：** Saga 补偿 + Redis Stream 死信队列双重保障。

**Saga 补偿流程：**

```
[任务 A 成功] → [任务 B 成功] → [任务 C 失败]
                                      ↓
                               [执行 C 补偿]
                                      ↓
                               [执行 B 补偿]
                                      ↓
                               [执行 A 补偿]
                                      ↓
                               [记录补偿结果]
                               [通知人工介入（如补偿失败）]
```

**死信队列 (DLQ) 设计：**

| 队列 | 用途 | 处理策略 |
|------|------|----------|
| dlq:user-domain | 用户中心模块失败消息 | 每小时重试，3 次后转人工 |
| dlq:recruit-domain | 招聘培训模块失败消息 | 每小时重试，3 次后转人工 |
| dlq:payroll-domain | 薪酬考勤模块失败消息 | 每小时重试，3 次后转人工 |
| dlq:auto-domain | 分析自动化模块失败消息 | 每小时重试，3 次后转人工 |

### 12.5 降级模式

**决策：** 当外部依赖不可用时，系统进入降级模式保障核心业务。

| 降级场景 | 降级策略 | 影响范围 |
|----------|----------|----------|
| LLM 服务不可用 | 使用规则引擎替代 AI 推理 | 简历筛选降级为关键词匹配 |
| OCR 服务不可用 | 暂停证件自动识别，允许后续补录 | 入职办理延迟，但不阻塞 |
| RPA 服务不可用 | 暂停外务自动操作，生成待办清单 | 社保/公积金操作延迟 |
| 人脸服务不可用 | 暂停人脸比对，使用证件号校验 | 签到功能降级 |
| 向量检索不可用 | 使用关键词检索替代 | 简历推荐精度下降 |

**降级例外条款（与 SRS 8.3 节一致）：**
- 降级期间的所有人工操作需完整记录至审计日志
- 降级原因和持续时间需纳入月度运维报告
- 降级因素消除后应立即恢复全自动化模式

### 12.6 告警机制

| 告警级别 | 触发条件 | 通知方式 | 响应时间 |
|----------|----------|----------|----------|

| P1 (高) | 服务性能下降 > 50%、熔断触发 | 短信 + 邮件 | 30 分钟内 |
| P2 (中) | 重试次数超限、死信队列积压 | 邮件 + 钉钉/企微 | 2 小时内 |
| P3 (低) | 常规异常、日志警告 | 邮件 | 24 小时内 |

## 13. 多租户隔离策略

### 13.1 多租户需求分析

**决策：** GBM AI Agent HR 系统当前为单租户部署，但架构设计预留多租户扩展能力。

**理由：**
1. GBM 为单一企业部署，当前无需多租户
2. 未来可能扩展为 SaaS 模式服务于多家企业
3. 预留多租户能力可降低未来改造成本

### 13.2 多租户架构设计（预留方案）

**隔离级别：** 数据库 Schema 隔离（逻辑隔离）

| 隔离级别 | 实现方式 | 优点 | 缺点 | 适用场景 |
|----------|----------|------|------|----------|
| 数据库隔离 | 每个租户独立数据库 | 最高隔离性 | 成本高 | 高端 SaaS |
| Schema 隔离 | 每个租户独立 Schema | 较高隔离性 | 中等成本 | 本系统预留方案 |
| 字段隔离 | 共享表，tenant_id 字段区分 | 成本最低 | 隔离性弱 | 低端 SaaS |

### 13.3 租户标识设计

**租户 ID 规则：** `TENANT` + `6 位数字`

| 租户 | 租户 ID | 说明 |
|------|---------|------|
| GBM (当前) | TENANT000001 | 默认租户 |

**实现方式：**

| 组件 | 实现 |
|------|------|
| 请求识别 | HTTP 头 `X-Tenant-ID` |
| 数据库路由 | MyBatis-Plus 插件自动注入 tenant_id |
| 缓存隔离 | Redis Key 前缀 `tenant:{tenant_id}:` |
| 文件隔离 | MinIO 路径 `/tenants/{tenant_id}/` |

### 13.4 租户数据迁移方案

| 场景 | 迁移方式 | 说明 |
|------|----------|------|
| 新增租户 | 自动创建 Schema + 初始化数据 | 部署脚本自动执行 |
| 租户数据导出 | 全量导出为 SQL + 文件包 | 用于备份或迁移 |
| 租户删除 | 软删除（标记为禁用） | 保留数据 30 天后可恢复 |

## 14. Agent 间通信机制 (V20 修订)

### 14.1 通信方式

| 通信方式 | 使用场景 | 机制 | 说明 |
|----------|----------|------|------|
| 包内方法调用 | 模块间同步调用 | Java 方法调用 | 如薪资查询、员工信息获取 |
| Spring Event | 进程内事件通知 | Spring 事件发布-订阅 | 如招聘完成通知、模块内事件 |
| Redis Stream | 跨实例事件广播 | Redis Stream 发布-订阅 | 如薪资发放完成、跨实例通知 |

### 14.2 包内方法调用设计 (V20 修订)

**决策：** 模块间同步调用采用包内方法调用，通过接口契约保证模块边界。

```
[用户中心模块] --(Java方法调用)--> [薪酬考勤模块]
    ↓ 接口: EmployeeService
    ↓ 包内访问控制
    ↓ 零网络开销
[返回员工基本信息]
```

**调用规范：**

| 规范项 | 规则 |
|--------|------|
| 超时时间 | 不适用（进程内调用） |
| 模块边界 | 通过接口抽象，禁止直接访问其他模块的实体类 |
| 请求格式 | Java 方法参数（DTO 对象） |
| 响应格式 | 统一响应包装 `{code, message, data}` |

### 14.3 Spring Event 异步事件设计 (V20 修订)

**决策：** 采用 Spring Event 作为进程内事件总线，Redis Stream 作为跨实例事件通道。

**事件类型设计：**

| 事件类别 | 事件名 | 用途 | 传播范围 |
|----------|--------|------|----------|
| 员工事件 | EmployeeOnboardedEvent | 员工入职完成 | 进程内 + Redis Stream |
| 员工事件 | EmployeeResignedEvent | 员工离职完成 | 进程内 + Redis Stream |
| 招聘事件 | ResumeScreenedEvent | 简历筛选完成 | 进程内 |
| 薪资事件 | SalaryCalculatedEvent | 薪资计算完成 | 进程内 + Redis Stream |
| 薪资事件 | SalaryPaidEvent | 薪资发放完成 | 进程内 + Redis Stream |
| 考勤事件 | AttendanceRecordedEvent | 考勤记录完成 | 进程内 |
| 培训事件 | TrainingCompletedEvent | 培训完成 | 进程内 |
| 证书事件 | CertificateExpiringEvent | 证书即将到期 | 进程内 |
| 绩效事件 | PerformanceEvaluatedEvent | 绩效评估完成 | 进程内 + Redis Stream |

**消息格式：**

```json
{
  "event_id": "evt_20260615_001",
  "event_type": "employee.onboarded",

    "dept_code": "DEPT001",
    "entry_date": "2026-06-15"
  }
}
```

### 14.4 Redis Stream 消息设计 (V20 修订)

**Stream 设计：**

| Stream | 用途 | 消费者组 | 保留策略 |
|--------|------|----------|----------|
| hr:employee:events | 员工事件（入职、离职、转岗） | user-domain, payroll-domain, auto-domain | 最大长度 10 万 |
| hr:payroll:events | 薪资事件（薪资计算完成、发放完成） | payroll-domain, user-domain, auto-domain | 最大长度 10 万 |
| hr:attendance:events | 考勤事件（打卡记录、异常） | payroll-domain | 最大长度 5 万 |
| hr:performance:events | 绩效事件（目标设定、评分完成） | payroll-domain, auto-domain | 最大长度 5 万 |

**消息可靠性保障：**

| 保障措施 | 实现方式 |
|----------|----------|
| 写入确认 | Redis Stream XADD 返回值确认 |
| 消费确认 | XACK 手动确认，处理完成后 ACK |
| 消息顺序 | 同一员工消息使用 emp_no 作为路由键 |
| 死信队列 | 消费失败 3 次后转入 dlq:{stream} |
| 消息追踪 | 消息元数据注入 TraceContext |
| 积压监控 | XPENDING 监控 pending 数量 |

```
                                                  ↓
                                           1. 创建员工档案

```

```
                                       ↓
                                1. Try: 冻结薪资金额
                                2. Confirm: 执行转账
                                3. 发布发放完成事件
                                       ↓
                                [Redis Stream: hr:payroll:events]
                                       ↓
                                [用户中心模块] 消费事件
                                       ↓
                                更新员工薪资记录
                                       ↓
                                [分析自动化模块] 消费事件
                                       ↓
                                更新财务报表
```

**3. 离职流程数据流：**

```
[用户中心模块] ──Spring Event: 离职申请──→ [内部流程]
                                               ↓
                                        1. 生成交接清单
                                        2. 通知相关部门
                                               ↓
                               [Redis Stream: hr:employee:events]
                                               ↓
                               [薪酬考勤模块] 消费事件
                                               ↓
                                        1. 计算最后薪资
                                        2. 停止社保/公积金
                                               ↓

                                               ↓
                                        1. 归档培训记录
                                        2. 释放招聘名额
                                               ↓
                               [用户中心模块] 完成离职
                                               ↓
                                        1. 更新员工状态
                                        2. 归档员工档案
```
